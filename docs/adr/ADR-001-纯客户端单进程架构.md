# ADR-001：纯客户端单进程架构（无中央服务器）

- 日期：2026-11-25 · 状态：♻️ **已修订** → 见 [ADR-006](ADR-006-多语言本地内核分层.md)（「纯客户端」仍成立，「单进程」不再成立） · 决策人：产品负责人
- 相关：[docs/00-设计基线.md §2](../00-设计基线.md) · [docs/01-架构设计.md §2](../01-架构设计.md)

## 背景

旧版 CBR-MAW 是 Python FastAPI + Next.js BFF + SDUI 的三段式部署：FastAPI 既是 API 又是静态托管，Next.js 做 BFF 与 manifest/page-spec 渲染，桌面版再套一层 WebView2/Tauri 外壳与 PyInstaller sidecar。产物有两个可执行体、两种语言、三套配置，桌面端还有独立的数据根路径与密钥目录。

用户对新产品形态的原始要求：「像 Codex 那样，没有中央服务器，能一个安装包 + 配个 api 密钥就可以快速使用，一键即用最重要」。

## 决策

1. **Flutter 应用是唯一的可执行体**，进程内承担数据层、采集、工具、知识检索、Agent 编排、LLM 调用与动态 UI 渲染的全部职责。
2. **不存在中央服务器、不存在 BFF、不存在需要单独部署的服务**。也不在 Dart 侧另起一个 `shelf`/`dart_frog` 服务进程——最初讨论中曾以「全 Dart 重写」为由考虑 Dart 服务端，经澄清后排除。
3. **不引入 Python**。旧项目的 Python 代码不迁移，只迁移**语义**（见 `docs/research/旧系统语义清单-迁移依据.md`）。
4. 数据、密钥、审计、模型产物全部落在**本机可写根**；Windows 为 `%LOCALAPPDATA%/CBR-MAW`，源码态回退仓库根；资源根只读。
5. 提供**工作区导出/导入**（不含明文密钥），避免数据被困死在单机。

## 后果

**正面**
- 分发形态极简：一个安装包 + 一个 API 密钥，无服务端运维、无网络依赖（除模型与来源站）。
- 消除旧版「三套配置 + 两条密钥路径 + 双语言构建链」的复杂度。
- 与 A2UI 路线天然契合：Agent 在本地生成 UI，不需要服务端推送 spec。
- 数据不出本机（除显式发往模型的字段），隐私边界清晰。

**负面 / 必须接受**
- **长驻抓取依赖 App 存活**。Windows 端用托盘常驻 + 开机自启补偿；Android 端受系统限制，只能前台定时 + 手动触发。
- **本地重算能力受限**：大模型推理、复杂 ML 只能走 API。
- 多人协作、跨机共享、集中审计均不支持（可由导出/导入部分缓解）。
- 单机资源上限即性能上限（见 `docs/09-工程化规范.md §11` 性能预算）。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 保留 Python FastAPI 后端 | 与「一键即用、无部署」直接冲突；保留两语言与两套构建链 |
| Dart 服务端（shelf/dart_frog）+ Flutter 客户端 | 同上；且需部署与鉴权，违背初衷 |
| Flutter 内嵌 Dart 本地服务（双进程） | 增加进程管理与 IPC 边界，收益不足 |
| 中央服务器 + 多用户 | 与「没有中央服务器」直接冲突 |
