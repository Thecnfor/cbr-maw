## 1. 角色体系

### 1.1 智能体与确定性组件

旧系统把「角色」定义为**业务主体的立场**（`configs/roles.yaml` 三条），而交叉验证在旧实现中是**同一批角色在第二轮里换一副 prompt 复核他人**（`configs/prompts/cross_validation.md` 的占位符 `{{display_name}}` 即证明它按角色渲染）。本文把这两层显式拆开：

| # | 身份 | Dart 类 | 性质 | 是否出结论 | 用 LLM |
|---|---|---|---|---|---|
| 1 | 监管方 | `lib/agents/roles/regulator_agent.dart` | 监管主体 | 出风险等级 + 监管关注建议 | 是 |
| 2 | 投资方 | `lib/agents/roles/investor_agent.dart` | 投资主体 | 出风险等级 + 仓位/对冲建议 | 是 |
| 3 | 融资方 | `lib/agents/roles/financing_agent.dart` | 融资主体 | 出风险等级 + 融资安排建议 | 是 |
| 4 | 交叉验证 | `lib/agents/roles/cross_validator.dart` | **复核者身份**（复用 #1–#3 的工具权限与证据包，以交叉验证 prompt 渲染） | 只出 `confirmed/refuted/uncertain`，不出风险等级 | 是 |

另有三个**非 LLM** 的确定性组件，它们不参与"多智能体"计数，但承担裁决、核验与准入职责：

| 组件 | Dart 类 | 职责 | 旧系统对应 |
|---|---|---|---|
| 协调者 | `lib/agents/orchestrator/` | 冲突仲裁（工具重算 > 权威证据 > HITL） | `orchestration/conflict.py` |
| 核验器 | `lib/agents/verification/` | 六类确定性核验 → `VerificationReport` | `verification/verifier.py` |
| 门卫 | `lib/agents/gate/` | JEV 裁判（封闭选项）+ 规则门卫回退 | `judgment/` |

> `[已定·本文]` 旧 `schemas.py` 的 `Role.COORDINATOR` / `Role.VERIFIER` 在新模型中**不是"有观点的智能体"**：
> `coordinator` → `Orchestrator`；`verifier`（旧系统"枚举存在但未实现"，无 RoleSpec、无智能体）→ `EvidenceVerifier` + `VerificationReport`。核验是确定性规则，不应消耗 token 或产生观点。

### 1.3 角色间冲突点矩阵

冲突不是"谁错了"，而是**同一 `subject` 上不同主体必然给出的不同答案**。这是系统的正常状态，系统必须能区分「事实冲突 / 方向冲突 / 偏好差异」。

| 冲突点 | 监管方视角 | 投资方视角 | 融资方视角 | 冲突类型 | 期望处理 |
|---|---|---|---|---|---|
| **压力概率阈值** | `high_stress_prob=0.50` | `0.45` | `0.40` | `preference` | 保留差异，不判错，分主体呈现 |
| **系统性 vs 组合层面** | 系统性风险优先 | 组合尾部损失优先 | 主体信用与再融资优先 | `preference` | 保留差异 |
| **同一波动率读数** | 视为外溢传导证据 | 视为尾部风险证据 | 视为融资成本传导证据 | `directional` | 追加工具证据（payload.direction）判定；无法判定 → HITL |
| **同一利差数值** | 不访问 `rates.credit`（越权） | 不在信息域 | 唯一有权访问者 | 单边事实（非冲突） | 由融资方为唯一权威来源，其余方不得复述 |
| **"该不该预警"** | 漏报 5.0 → 倾向早报 | 尾部 5.0 vs 交易成本 1.0 → 报告但不激进调仓 | 成本超支 3.0 → 倾向保守安排 | `preference` | 保留差异 |
| **组合头寸 / 融资事件** | 明确禁止访问 | 可见 `portfolio.exposure` | 可见 `financing.events` | 越权（非冲突） | 核验器记 `permission` 违规 → HITL |
| **数值一致性** | 同一 subject、同一工具、同一 as_of | 同左 | 同左 | `fact` | 工具重算为准：胜者 `verified`，败者 `rejected` |
| **卡级风险等级差异** | 等级不同 | 等级不同 | 等级不同 | **不算冲突** | 卡级差异不进入 `detect_conflicts`；只有 claim 级才判 |

> `[已定·本文]` 冲突检测以 **`subject` 归一化字符串**（去空格、小写、下划线连接）为分组键，且**只做跨角色的 claim 级比对**；同一角色内部不产生冲突；**卡级风险等级差异不判为冲突**。

### 1.4 system prompt 要点（从旧 prompt 提炼语义，非照抄）

旧 prompt 模板 = `configs/prompts/{role}.md`（角色骨架，含 `{{objective}}` 等占位符）+ `configs/prompts/common_rules.md`（三角色共享的证据规则与输出 JSON schema）。新 Dart 侧由 `PromptBuilder` 在运行时把 `RoleSpec` 字段渲染进模板。

**共通部分（`common_rules.md` 语义）**：

1. **角色是"分析解释者"，不是"计算者"**：所有数值必须逐字复制证据包中 `kind=tool` 或 `kind=signal` 的 `value` 与 `unit`，禁止重算/外推/编造。
2. **最终风险等级由系统按角色阈值确定性判定**，LLM 的 `risk_level_assessment` 只是参考，且不得与证据矛盾。
3. **每条 claim 必须绑定 `evidence_ids`**，且只能引用证据包中出现的 `evidence_id`。
4. `numeric` claim：`value`/`unit` 与证据完全一致，`text` 中除该数值外不得出现其他数字。
5. `text` claim：必须绑定 `kind=kb` 证据，只做概括与引用，不得虚构政策条文/发布日期/机构名称。
6. `directional` claim：必须绑定 `kind=signal` 或数值证据，给出 `up/down/flat/none`。
7. 证据不足 → 写入 `limitations`，**不用 claim 表达无法溯源的判断**。
8. 禁止输出证据包之外的时间、比例、金额、排名、政策条款编号；禁止具体个股买卖建议；禁止对未来收益作确定性承诺。
9. 数量与语气：claims 3–6 条；有数值证据则至少 1 条 `numeric`；有 KB 证据则至少 1 条 `text`；中文、专业、克制；不确定时明说"证据不足"。

**各方角色专属语气**：

| 角色 | 表达顺序 | 建议边界 | 必须交代的权衡 |
|---|---|---|---|
| 监管方 | 先风险等级 + 压力概率证据 → 再外溢渠道 + 关键驱动 | 监测频率 / 跨部门会商 / 压力测试 / 宏观审慎措施；不评价单只个股 | 误报 vs 漏报 |
| 投资方 | 先组合层测度（波动、VaR/CVaR、回撤、相关性）→ 再仓位/对冲/风险预算 | 面向组合整体与风险预算；不给个股指令；不承诺收益 | 交易成本、对冲成本 vs「过早离场 vs 尾部保护」 |
| 融资方 | 先融资成本变化、信用利差、再融资窗口、现金流缓冲 → 再融资安排 | 锁定成本 / 久期管理 / 备用授信 / 现金流缓冲；不评价市场交易头寸 | 再融资风险 vs 过度对冲 |
| 交叉验证 | 先给每条证据的 `verdict` → 再给 `note`（依据 ≤80 字） | 只复核 `peer_facts`；`recomputed_value` 只抄录 | 不适用 |

**新 prompt 的三处工程化改造** `[已定·本文]`：

| 改造 | 原因 | 做法 |
|---|---|---|
| **结构化输出取代 markdown JSON 块** | 旧 prompt 让模型手写 JSON，解析失败率高 | 用 Genkit 的结构化输出绑定 schema，模型只填字段不写 JSON |
| **证据包由代码注入为结构化字段** | 旧 prompt 里证据是文本拼接，易丢字段 | `EvidencePacket` 以 JSON 注入 user prompt，含 `evidenceId/kind/value/unit/source.releaseTime` |
| **紧凑提示** | 基线 §3 风险 2：`PromptBuilder.chat()` 可能产出 3,000–5,000+ tokens | **不使用** `PromptBuilder.chat()` 全量提示；按 `systemPromptFragments` 只注入所需片段（见 `01-架构设计.md` §3.3） |

**证据 ID 与哈希规范** `[已定·本文]`（必须**逐字节复刻**旧规范，否则证据链不可复现、旧证据不可迁移）：

```
tool 证据： evidence_id = "ev_tool_${tool}_${YYYYMMDD}_${inputs_hash.substring(0,12)}"
            inputs_hash  = sha256(canonicalJson{tool, version, as_of, params})
            evidence.hash= sha256(canonicalJson(payload))
其他 kind ： evidence_id = "ev_${kind}_${YYYYMMDD}_${hash.substring(0,12)}"   // [建议·待复核] 具体前缀待与 05 文档对齐
```

**黑板三级去重 + 别名** `[已定·本文]`（继承旧 `canonical_evidence_key`）：

| 级别 | 去重键 | 行为 |
|---|---|---|
| 1 | `evidence.hash` | 命中 → 视为同一条 |
| 2 | `tool.inputs_hash` | 命中 → 视为同一次工具计算 |
| 3 | 内容哈希 | `sha256(canonicalJson{kind, as_of, title, summary, value, unit, payload, source, tool})` |

命中时**保留最早出现的 id 作为规范 id**，异名登记为**别名**，可经 `resolve_id` 解析到规范 id。

**证据权威等级** `[已定·本文]`（继承旧 `evidence_grade`）：

| kind | grade | 含义 |
|---|---|---|
| `tool` | **3** | 确定性工具输出，可按 `inputsHash` 重算 |
| `kb` / `policy` | **2** | 知识库片段 / 政策原文，带 `releaseTime` |
| `signal` / `market` | **1** | 共享信号 / 行情快照 |
| （无证据） | 0 | 不可作为裁决依据 |

### 1.7 自检回填规则（LLM 草稿 → Claim）

> `[已定]` 迁移清单 A.1：**这是整套系统的信任根基**。LLM 只产草稿，数值由证据回填。

| claim 类型 | 回填规则 | 无对应证据时 |
|---|---|---|
| `numeric` | `value`/`unit` **一律以 `kind=tool` 证据覆盖** | **直接丢弃**，记 `claim_rejected` trace |
| `text` | 必须绑定 `kind=kb` 证据；只做概括与引用 | **丢弃** |
| `directional` | 必须绑定 `kind=signal` 或数值证据 | **丢弃** |
| 全部 | LLM 给的 `evidenceIds` 不在证据包内 → **过滤** | 过滤后为空 → **丢弃** |

> 由此推出两条硬规则：
> 1. **模型不得自行给出数值**——它给出的数值会被证据覆盖，模型给错不改变结论；
> 2. **丢弃是常态而非异常**——被丢弃的 claim 要留 `claim_rejected` trace，UI 上不展示，但审计可查。

### 1.8 风险等级的**确定性**判定（不由 LLM 决定）

判定分两步，顺序固定 `[已定·本文]`：

**第 1 步 · 由压力概率定基准等级**

```
p = signal.horizons[roleSpec.horizonDays]   // 缺该窗口时取最近窗口；再缺则用 signal.percentile
high      = roleSpec.thresholds['high_stress_prob']     // 缺省 0.5
critical  = roleSpec.thresholds['critical_stress_prob'] // 缺省 min(0.95, high + 0.2)

p >= critical     → critical
p >= high         → high
p >= high * 0.5   → medium
否则               → low
```

**第 2 步 · 关键工具证据越阈升级（+1 级，封顶 critical）**

```
对 published 证据中 kind==tool 且 value!=null 的条目：
  若 evidence 文本命中该角色的升级关键词，且 |value| >= 阈值
  → 风险等级上调一级，触发证据 id 记入 RiskCard.escalationEvidenceIds
```

| 角色 | 阈值键 | 命中关键词 |
|---|---|---|
| regulator | `dy_spillover` | `spillover`, `溢出`, `dy_`, `systemic`, `传染` |
| investor | `max_drawdown` | `drawdown`, `回撤`, `cvar`, `var`, `尾部` |
| financing | `funding_cost_jump_bp` | `funding`, `spread`, `利差`, `融资` |

> `[已定]` 基线 §7.1 的「取更强风险」在**动作**语境下指「spec 与 catalog 中更强的风险」（见 §5.2）；在**判定**语境下指三角色风险等级合成为最终卡片时取更强者（见 §2.4 R5）。两者都落地为"取 max"的确定性规则。

**决策损失分解**（`decisionLoss`，**预期损失而非金额**，UI 文案须保留免责）：

```
对每个权重名 w：
  side = silent 若 w ∈ {miss, missed_exit, tail_loss, cost_overrun, liquidity_shortfall, delay}
         warn   若 w ∈ {false_alarm, transaction_cost, over_hedging}
  factor = p (silent 侧：报警则付出该损失) / (1 - p) (warn 侧：不报警则付出该损失)
  components['expected_$w'] = round(w * factor, 6)
components['if_warn_total']     = Σ(warn 侧)
components['if_silent_total']   = Σ(silent 侧)
components['recommended_total'] = (等级 ≥ high) ? if_warn_total : if_silent_total
components['signal_probability']= p
```

**`limitations` 的系统级自动追加** `[已定]`（≤8 条，UI 展示这段而非只展示 LLM 写的）：等级由规则判定、claim 数值已回填、决策损失非金额、KB 不可用、工具部分失败、角色降级、模型调用模式提示。

### 2.3 各阶段的输入 / 输出 / 失败处理

#### R0.0 意图路由 + 门卫

```dart
final class ResearchIntent {
  final IntentKind intent;      // fullWarning | askRole | askEvidence | explainDecision | compare
  final DateTime asOf;          // 用户未指定 → 取数据层最新可得 as_of（非「今天」）
  final CollaborationMode mode;  // 用户指定 → 用指定；否则取配置默认
  final List<RoleId> roles;      // askRole 时为单角色；否则为全部启用角色
  final String question;
  final BudgetPlan budgetPlan;
  final GateInfo gate;          // 门卫结果：judge / rule、available、note
}
```

- **输入**：`UserTurn{message, asOf?, modeHint?, selectedRole?}`。
- **输出**：`ResearchIntent`。
- **失败处理**：
  - 意图不可判 → 默认 `fullWarning`，对话流追加**纯文本**澄清问句（不建 surface，避免无谓动作）。
  - `asOf` 缺失 → 取数据层最新可得 `as_of`；数据层为空 → 直接进入 R0.1 的"全失败"分支。
  - **绝不**因为意图不明就自行改变 `mode`（消融可比性依赖 mode 由配置决定）。
  - **门卫**（`lib/agents/gate/`）：JEV 可用时用 `choice` 问题判「探索 / 新决策 / 越界」，`confidence >= 0.6` 才放行；**JEV 不可用时回退规则门卫，规则门卫不产出置信度，并在 `note` 明说「未使用模型判断」**；`judge_availability()` **只查配置、不发网络请求**。门卫结果落审计。

#### R0.1 工具/数据检索

```dart
final class RetrievalStage {
  final ToolRegistry tools;
  final KnowledgeBase kb;
  final DataProvider provider;
  Future<EvidencePacket> run(ResearchIntent intent, RoleBudget budget) async;
}
```

- **输入**：`ResearchIntent` + 角色信息域并集。
- **输出**：`EvidencePacket`（每条 `Evidence` 带 `asOf`；文本证据带 `source.releaseTime ≤ asOf`；KB 证据必须带 `chunkId` 与 `publishTime`）。
- **失败处理**：
  - 单个工具抛错 → `ToolResult{ok:false, error}`，**不产生 Evidence**，记 `tool_call` + error。
  - 知识库检索为空 → 允许继续，但 `text` 类 claim 不可产生（prompt 规则 + 自检回填 + 核验三重约束）。
  - 全部来源失败 → 抛 `NoUsableEvidence`；编排层终止 run，UI 显示**只读错误卡**（无 action），文案说明「本地数据源当前不可用」，**不产出任何风险结论**。

#### R0.2 角色并行分析

- **输入**：每个角色一份 `AgentInput`；**共享同一份基础 `EvidencePacket`，但不含对方结论**。
- **输出**：`List<AgentOutput>`。
- **权限与越权** `[已定]`：
  - 工具注册表提供**两套入口**，刻意区分：
    - `registry.run(role, toolName, args)` → **带权限矩阵**，`default_deny=true`，未知角色/未知工具一律拒绝；越权 → 返回 `ok=false` + `data.disallowed=true`，写 `tool_denied` trace，**绝不执行**。
    - `registry.get(toolName).run(args)` → **绕过权限**，仅供**核验重算**使用（R2.1 / R4.1 的权威重算走这条）。
  - 信息域越权（claim 引用了角色信息域外的证据）→ 由核验器记 `permission` 违规。
- **失败处理**：
  - 单角色异常 → `AgentOutput{status: failed}`，**不产出规则模板卡片**，不影响其他角色。
  - 单角色超时 → `status: timeout`；该角色在最终卡中缺席，`degradedRoles` 列出并写 trace。
  - **零 Mock 严格模式**：`allow_mock=false` 时 LLM 失败**必须失败退出**，不得用规则模板冒充模型结论。

#### R1 证据共享

- **输入**：各角色的 `AgentOutput.evidence` + 共享信号证据（`producedBy='coordinator'`）。
- **输出**：黑板快照 + `evidenceShared` / `duplicateEvidence` 计数。
- **去重与别名**：三级去重（§1.6.4），保留最早 id 为规范 id，异名登记别名并可 `resolve_id` 解析。
- **失败处理**：纯函数，无失败路径。

#### R2 交叉验证（**双轨，缺一不可**）

| 轨 | 执行者 | 动作 | 结果 |
|---|---|---|---|
| **R2.1 工具重算**（确定性） | 编排器代表被分配角色执行 | 对 peer 最高置信的 `numeric` claim 用权威工具重算 | 匹配 → 胜者 `verified`；不匹配 → **合成 `recheck_*` claim**（权威性评分 **+10**）+ 原 claim 置 `conflicted` |
| **R2.2 LLM 互评**（复核者身份） | 每个角色以 `crossValidator` prompt 渲染 | 对 peer 证据出 `verdict` | `refuted` → 对方数值 claim 降级 `unverified`；`confirmed` → 升 `verified`；`uncertain` → 保持 `unverified` |

```dart
final class CrossValidationFinding {
  final String evidenceId;       // 必须来自 peerFacts
  final Verdict verdict;         // confirmed | refuted | uncertain
  final String note;             // ≤ 80 字，含工具名/版本/时点/口径
  final double? recomputedValue; // 只能抄录 peer 证据中已出现的数值，否则 null
}
```

- **输入**：peer 角色的 `RiskCard.claims` 与其 `evidenceIds`（作为 `peerFacts`）。
- **输出**：`List<CrossValidationFinding>`，每角色**最多 2 条**，优先复核"对本角色决策影响最大"的数值主张。
- **失败处理**：
  - 模型输出不符合 schema → 重试 1 次；仍失败 → 该条记 `uncertain`，`note` 写「复核未完成」。
  - 复核方引用了不存在的 `evidenceId` → **丢弃该 finding** 并记 `citation` issue。
  - 复核方无该 subject 的工具权限 → `uncertain`，`note` 写「本角色无该口径复核权限」。
  - R2.1 工具重算失败 → 该条降级为 `uncertain`，**不得**用其他工具的结果冒充。

#### R3 分歧识别

```dart
final class Conflict {
  final String conflictId;      // cf_<seq>
  final String subject;         // 归一化 subject
  final List<String> claimIds;
  final List<RoleId> roles;
  final ConflictType type;      // fact | directional | preference
  final String description;
  final Severity severity;      // low | medium | high
  final List<String> evidenceIds;
  bool resolved; String resolution; ResolvedBy? resolvedBy;
}
```

| 类型 | 判定条件 | severity |
|---|---|---|
| `fact` | 同 `subject`、单位可比、两者均为 `numeric`、数值不相等（超出容差 `absTol=1e-6` / `relTol=1e-3`）、且**不共享证据** | **相对差 > 5% → high**，否则 medium |
| `directional` | 同 `subject`、方向字段相反（`up` vs `down`） | **共享同一证据 → high**，否则 medium |
| `preference` | 证据一致（同 `evidenceIds` 有交集）或数值相容，但角色 `thresholds` / `decisionLossWeights` 不同 | **low**（不算错误、不计入核验错误率） |

- **每个 subject 至多 1 条冲突**；跨角色两两分类，优先级 `fact > directional > preference`。
- **peer refuted 的冲突强制升 `high`**。
- **卡级风险等级差异不判为冲突**。
- **失败处理**：纯函数。若某 claim 的 `subject` 为空 → 跳过。

#### R5.1 六类核验

```dart
final class VerificationReport {
  final String runId;
  final int numericChecksTotal, numericChecksPassed;
  final int citationChecksTotal, citationChecksPassed;
  final int semanticChecksTotal, semanticChecksPassed, semanticUnverified;
  final int unsupportedClaims, permissionViolations, leakageEvents, schemaErrors;
  final List<VerificationIssue> issues;   // numeric|citation|leakage|permission|schema|unsupported|semantic
  final bool passed;
}
```

| 检查 | 判定 | severity |
|---|---|---|
| `numeric` | claim 的 `value/unit` 必须与所绑 `kind=tool|signal` 证据在容差内一致；`text` 中出现的数字必须全部来自证据 | error |
| `citation` | 每条 claim 的 `evidenceIds` 非空且全部存在于证据索引；**KB 证据缺 `chunkId` 或 `publishTime` 直接判失败** | error |
| `leakage` | 证据 `asOf > decision.asOf` 或 `source.releaseTime > decision.asOf` | error（**硬错误**） |
| `permission` | claim 引用了角色信息域之外的证据，或调用了白名单外的工具 | error |
| `schema` | 输出结构不符合 `RiskCard`/`Claim` schema | error |
| `unsupported` | `text`/`directional` claim 未绑定对应 kind 的证据 | warning |
| `semantic` | 文本 claim 的概括超出证据原文可支持范围（四分类：supports / contradicts / unsupported / fabricated） | warning |

**`passed` 判定**：`numericErrorRate == 0 && permissionViolations == 0 && leakageEvents == 0 && schemaErrors == 0`。

> `[建议·待复核]` `semantic` 检查在旧系统里由 JEV 实现但**未接入生产链路**（迁移清单第 60 条）。本代建议接入，JEV 不可用时回退规则门卫（无置信度、明说未使用模型判断）。

#### R5.2 合成

- **输入**：三张 `RiskCard`（含 `degradedRoles` 标记）、已仲裁 `Conflict`、`VerificationReport`、`CoordinationStats`。
- **输出**：`DecisionCard{runId, asOf, mode, signal, cards, evidence, conflicts, verification, coordination, finalLevel, finalAdvice, traceRef, createdAt}`。
- **finalLevel（取更强风险）**：`max(cards[*].riskLevel)`；**降级角色不参与 max**（避免拉高整体），但要在 `finalAdvice` 的「降级说明」中列出。
- **失败处理**：**LLM 合成失败 → 失败退出**，产出显式错误，**不得用规则模板冒充模型结论**（迁移清单第 29 条）。模板只允许用于**渲染兜底**（LLM 成功但渲染失败时的展示降级），且模板**只复述已核验字段**，不新增任何数值。

### 2.4 三种协作模式（消融的代码路径统一）

`[已定]` 基线 §7.9：模态/角色/协作模式均可配置化对照实验，而不是硬编码。因此三模式**必须是同一条代码路径**，只由 4 个开关控制：

```dart
// lib/agents/orchestrator/mode_flags.dart
final class ModeFlags {
  final CollaborationMode mode;
  final bool useSingleAgent;   // single=true
  final bool shareEvidence;    // collaborative=true
  final bool crossValidate;    // collaborative=true
  final bool coordinate;       // collaborative=true
  final bool pseudoSpecialize; // 伪分工对照（E8）
}

const Map<CollaborationMode, ModeFlags> kModeFlags = {
  CollaborationMode.single:        ModeFlags(single,         useSingleAgent: true,  shareEvidence: false, crossValidate: false, coordinate: false, pseudoSpecialize: false),
  CollaborationMode.independent:   ModeFlags(independent,    useSingleAgent: false, shareEvidence: false, crossValidate: false, coordinate: false, pseudoSpecialize: false),
  CollaborationMode.collaborative: ModeFlags(collaborative,  useSingleAgent: false, shareEvidence: true,  crossValidate: true,  coordinate: true,  pseudoSpecialize: false),
};
```

| 阶段 | single | independent | collaborative |
|---|---|---|---|
| R0.2 | **一个**通用 agent 依次完成三个主体的任务（工具权限并集、同一份预算池） | 三个角色 agent，互不可见 | 三个角色 agent，互不可见 |
| R0.1 | 执行一次 | 执行一次（同一份证据包） | 执行一次 |
| R1 | 跳过 | 跳过 | 执行 |
| R2 | 跳过 | 跳过 | 执行 |
| R3 | 跳过 | 跳过 | 执行 |
| R4 | 跳过 | 跳过 | 执行 |
| R5 | 执行 | 执行 | 执行 |

- `pseudoSpecialize=true`（E8 伪分工对照）：三个 agent **共用同一 prompt 与同一工具权限并集**，仅在结论里声明"我是监管主体"。用于分离"专业化收益"与"多 agent 收益"。
- **预算一致性** `[已定]`：三种模式**每角色** `maxToolCalls=6`、`maxTokens=4000` 一致；一次 run 总预算 = 承担的主体任务数 × 每角色上限（三种模式均为 3）。

## 3. 多智能体委派（`package:genkit_middleware/agents.dart`）

### 3.1 委派协议（orchestrator ↔ subagent）

```
                    ┌───────────────────────────────────────┐
                    │  Orchestrator（编排者 agent）          │
                    │  system prompt 末尾自动追加：          │
                    │  <sub-agents>                         │
                    │    - regulator: 监管主体…              │
                    │    - investor: 投资主体…               │
                    │    - financing: 融资主体…              │
                    │  </sub-agents>                        │
                    │  工具：delegate_to_regulator           │
                    │        delegate_to_investor            │
                    │        delegate_to_financing           │
                    └──────────────┬────────────────────────┘
                                   │ LLM 决定调用哪个委派工具
                                   │ 调用参数 = {"task": "..."}
                                   ▼
                    ┌───────────────────────────────────────┐
                    │  agents() 中间件                       │
                    │  1. 解析目标子代理                     │
                    │  2. 按 historyLength 转发父会话历史     │
                    │  3. 以 task 调用子代理                 │
                    │  4. 按 artifactStrategy 处理 artifact  │
                    │  5. 把子代理返回作为工具结果回灌父会话 │
                    └──────────────┬────────────────────────┘
                                   ▼
                    ┌───────────────────────────────────────┐
                    │  Subagent（regulator/investor/…）     │
                    │  输出：RiskCard + Evidence + Artifact │
                    └───────────────────────────────────────┘
```

> `[已定]` ADR-003：**委派能力封装在我方 `AgentDelegation` 接口后**，替换中间件实现不影响上层（`genkit_middleware/agents.dart` 不在语义化版本保证内）。

### 3.2 委派 artifact schema

子代理除返回文本结论外，还要产出**结构化 artifact**，供编排层独立检查与 UI 渲染。`artifactStrategy` 决定 artifact 内容是否进入工具结果文本。

```dart
// lib/agents/orchestrator/delegation/role_artifact.dart
final class RoleArtifact {
  final String schemaVersion;     // "cbr.role-artifact/1"
  final String runId;
  final RoleId role;
  final int round;
  final String asOf;              // ISO 日期
  final RiskLevel riskLevel;      // 系统确定性判定值
  final String headline;
  final List<ArtifactClaim> claims;
  final List<ArtifactEvidenceRef> evidenceRefs;
  final List<String> limitations;
  final List<String> toolCalls;   // 工具名 + inputsHash（不写参数值，避免泄敏）
  final TokenUsage tokens;
  final int latencyMs;
  final String promptHash;        // 本次 system+user prompt 的哈希（可复现性锚点）
  final String modelId;           // 例如 deepseek-chat
}

final class ArtifactClaim {
  final String claimId;
  final ClaimType claimType;
  final String subject;
  final String text;
  final double? value; final String? unit; final Direction? direction;
  final List<String> evidenceIds; // 必须 ⊆ evidenceRefs
  final double? confidence;
}

final class ArtifactEvidenceRef {
  final String evidenceId;
  final EvidenceKind kind;
  final String? toolName, toolVersion, inputsHash;
  final String? sourceName, sourceUrl, releaseTime;
}
```

**约束** `[已定·本文]`：

1. `claims[].evidenceIds ⊆ evidenceRefs[].evidenceId` —— 越界即 schema error。
2. `riskLevel` 由**系统**填入，不由子代理自填（子代理只提供 `riskLevelAssessment` 作为参考字段）。
3. `promptHash` + `modelId` + `toolCalls[].inputsHash` 三者足以**重放**一次研判。
4. artifact 不含任何 UI 指令；UI 由编排层另行生成（**Agent 不直接产出未登记组件**）。

### 3.3 委派预算参数

| 参数 | 取值 | 依据 |
|---|---|---|
| `maxDelegations` | **3** | 三角色各一次；三模式可比性要求（与"每角色 6 次工具调用"预算对齐，见 §6.3）。`[建议·待复核]` |
| `historyLength` | **0** | 父会话历史不进子代理。理由：R0.2 要求三角色**互不可见**，转发历史会引入跨角色泄漏。子代理需要的上下文由 `AgentInput.evidence` 显式给出。`[已定·本文]` |
| `artifactStrategy` | **`session`** | artifact 内容合并进父会话（可被后续阶段独立检查与渲染），工具结果只报 artifact 名与 id，**避免 token 二次膨胀**。`[建议·待复核]` |
| `async` | **false** | 纯客户端单进程；三角色并行由 Dart `Future.wait` 在 R0.2 内做。Genkit 的后台委派需要 server-managed session store，与基线 §2「纯客户端单进程」冲突，**本代不启用**。`[已定]` |

### 3.4 为什么在编排层之外还要用委派中间件

| # | 理由 | 具体收益 |
|---|---|---|
| **1** | **artifact 可独立检查** | 委派中间件把每个子代理的产出收敛为一份带 `schemaVersion` 的 artifact，编排层能在**不重跑 LLM**的情况下校验（`claims.evidenceIds ⊆ evidenceRefs`、`riskLevel` 是否被篡改、`promptHash` 是否可重放）。若子代理直接在父会话里流式吐文本，编排层只能靠解析自由文本校验——这在论文里无法作为「证据链可核验」的证据。 |
| **2** | **避免上下文爆炸** | `artifactStrategy:'session'` + `historyLength:0` 使父会话只拿到 artifact 名与 id；子代理不继承父历史；证据包按需裁剪。R0.2→R5 的总 token 可预测地落在预算内，而不是随「角色数 × 证据量」线性膨胀。 |
| **3** | **委派是编排器的一个可关掉的机制** | 消融需要「有/无委派」这一维：`independent` 模式**不注册** `agents()` 中间件，三角色由编排层直接并行调用；`collaborative` 注册，委派由 LLM 决定参与角色。若没有中间件，这一维只能在编排层硬编码两套路径，破坏"同一代码路径"原则。 |
| **4** | **失败语义被中间件收敛** | 子代理失败或触发 interrupt 时，中间件把失败/暂停**作为委派工具的输出返回给编排器**，不会自动冒泡成顶层错误。编排器因此可按 prompt 指示选择「继续 / 换专家 / 修正输入 / 回报用户」——正对应 §10 的「部分角色失败」策略。 |

> **与编排层的边界** `[已定·本文]`：编排层负责**何时**研判（意图、时点、模式）、**证据去哪取**、**冲突怎么裁**、**预算怎么算**；委派中间件负责**单次角色任务如何被调起、产出如何被收敛为 artifact**。二者不重叠。

## 4. 冲突消解与证据核验

### 4.1 旧语义 → 新机制翻译表

| 旧系统语义 | 旧实现位置 | 新机制（Dart + A2UI） |
|---|---|---|
| 取更强风险 | 判定层汇总 / 动作 `strongerRisk()` | 判定层：`finalLevel = max(cards.riskLevel)`（§2.3 R5.2）；动作层：`ActionDispatcher` 对组件声明与动作注册表取 max（§5.2） |
| fail-closed | `renderer/src/actions.ts`：缺 confirm handler → 拒绝执行 | `ActionDispatcher`：L1/L2 缺确认处理器 → **拒绝执行并记录审计**；核验侧：缺证据 → claim 不得进入最终建议 |
| 证据必须可回指 | `verifier.py::_check_claim_citation` | `Claim.evidenceIds` 非空 + `citationChecksPassed == citationChecksTotal`；UI 上每条 claim 渲染为可点击的证据链接 |
| HITL | `orchestration/hitl.py`：`HITLQueue` + `approve/reject/override` | `lib/agents/orchestrator/hitl/hitl_queue.dart` + A2UI 确认卡；动作回写 trace |
| 偏好差异不判错 | `conflict.py::_resolve_preference` | `ClaimStatus.preference`，`Conflict.severity=low`，**不计入** `numericErrorRate` |
| `recheck_*` 合成 claim | `rounds.py` 工具重算产物 | 保留 `recheck_` 前缀语义 + **权威性评分 +10** |

### 4.2 冲突的本地状态机

```
                 ┌───────────┐
   detect ──────►│ detected  │
                 └─────┬─────┘
                       │ arbitrate
         ┌─────────────┼──────────────┬───────────────┐
         ▼             ▼              ▼               ▼
   ┌───────────┐ ┌───────────┐  ┌───────────┐   ┌───────────┐
   │ resolved  │ │ resolved  │  │ escalated │   │ unresolved│
   │ by=tool   │ │ by=authority│ │ (HITL)   │   │ (证据不足)│
   └─────┬─────┘ └─────┬─────┘  └─────┬─────┘   └─────┬─────┘
         │             │              │              │
         │             │              │        补证据后重入 arbitrate
         │             │              │              │
         └─────────────┴──────────────┴──────────────┘
                       ▼
                 ┌───────────┐
                 │ finalized │  ← 仅当 resolved 或人工处置完毕
                 └───────────┘
```

| 转换 | 触发 | 处理 | trace |
|---|---|---|---|
| `detected → resolved(tool)` | `fact` 冲突且找到权威工具 | 用权威工具重算（走 `registry.get(name).run()` 绕过权限），产新 `Evidence`（`kind=tool`，带 `inputsHash`）。数值一致 → 胜者 `verified`、败者 `rejected`；不一致 → 以工具值为准并把差异写入 `resolution` | `conflict_resolved` |
| `detected → resolved(authority)` | `fact` 冲突但无对应工具 | 按 `evidence_grade` 取高者（tool 3 > kb/policy 2 > signal/market 1）为胜者，败者 `rejected`；`resolution` 说明证据等级差异 | 同上 |
| `detected → resolved(consensus)` | `preference` 冲突 | 双方 `status=preference`，`severity=low`，**不算错误**，分主体呈现 | 同上 |
| `detected → escalated` | `directional` 冲突且补证后仍相反；或 `fact` 冲突且无工具、双方证据等级相同 | 生成 `HitlItem{kind:'unresolved_conflict'}`，UI 发确认卡 | `conflict_escalated` |
| `detected → unresolved` | 证据不足，无法判定且已用尽重试 | 保留冲突，`resolvedBy='unresolved'`，**不进入合成结论** | `conflict_unresolved` |

**subject → 权威工具映射** `[已定·本文]`（继承旧 `SUBJECT_TOOL_RULES`，顺序敏感，越具体越靠前）：

| 关键词（subject 含） | 权威工具 |
|---|---|
| `northbound`, `southbound`, `capital_flow`, `ah_premium`, `资金`, `北向`, `南向`, `跨境` | `capital_flow` |
| `funding`, `credit_spread`, `refinanc`, `利差`, `融资`, `信用` | `funding_cost` |
| `spillover`, `covar`, `correlation`, `systemic`, `外溢`, `传染`, `相关性` | `systemic_risk` |
| `var`, `cvar`, `drawdown`, `volatility`, `最大回撤`, `波动`, `回撤` | `risk_measure` |
| `stress_prob`, `probability`, `prob_high`, `预测概率`, `高压力概率` | `forecast` |
| `scenario`, `情景`, `冲击` | `scenario` |
| `policy`, `regulation`, `政策`, `监管`, `资本管制` | `knowledge_search` |
| `trend`, `direction`, `方向`, `趋势` | `systemic_risk` |
| （兜底） | `risk_measure` |

> 映射命中后若该工具**不在当前角色的工具白名单**内 → 仲裁降级为 `authority`（不用越权工具），并在 `resolution` 记录「该口径权威工具不在本角色权限内」。**绝不**为了裁决而放宽白名单。

### 4.3 冲突如何呈现给用户

| 冲突状态 | A2UI 呈现 | 位置 |
|---|---|---|
| `preference`（已解决，保留差异） | 三角色卡片内各显示自己的判定，**不弹卡**；在「分歧」小节以对照表列出 | 主 surface 的 `conflicts` 子树 |
| `fact`（已解决） | 冲突条目显示「以工具重算为准」，附胜出证据链接与败者数值 | 同上 |
| `fact` / `directional`（升级 HITL） | **弹确认卡**：并列显示双方主张 + 各自证据 + 仲裁失败原因 + 三个动作按钮 | 独立 surface `cbr.hitl.<itemId>` |
| `unresolved` | 冲突条目标「未解决」，最终建议中显式列出（不可隐藏） | 同上 + 最终卡 |

**「谁裁决」的明确回答** `[已定·本文]`：

1. **工具重算**优先（可复现，最高权威）；
2. **权威证据等级**次之；
3. **偏好差异不由人裁决**——它不是错误，分主体呈现即可；
4. **剩余情况由人裁决**（HITL），且**人工不改变事实，只做处置**：允许「驳回相关结论（不计入最终建议）」「确认维持」「按人工给定替换」三种；不允许人工凭空写入新的数值主张（那会制造无依据断言）。

### 4.4 哪些必须人工确认

| 事项 | 是否必须人工 | 理由 |
|---|---|---|
| 未解决的事实冲突 | **是** | 两个同等权威的数值无法自动取舍 |
| 方向冲突且补证后仍相反 | **是** | 影响最终等级方向 |
| 越权访问（permission violation） | **是** | 提示可能有信息泄漏或角色混淆 |
| 时点泄漏（leakage） | **是** | 影响全部结论可信度 |
| 核验不通过（schema / unsupported 超过阈值） | **是** | 结论不可采信 |
| 任一角色或共享信号为 `critical` | **是**（标记「需人工复核」，不阻塞） | 旧语义 `high_risk → escalate` |
| L2 动作执行 | **是** | 基线 §7.1 |
| L1 动作执行 | **是**（确认即可，不需审计事件） | 基线 §7.1 |
| L0 动作 | 否 | 纯导航/只读 |
| 预算超限 | 否（仅记录 + 最终卡提示） | 旧语义 `budget_exceeded → record` |

## 5. 风险分级与动作模型（L0/L1/L2）

> 本节的 L0/L1/L2 是**动作风险分级**（基线 §7.1、`01-架构设计.md` §5.4），与 §1.8 的 `low/medium/high/critical` **风险等级**是两套语义。文中一律用「动作风险级 L*」与「风险等级」区分。

### 5.1 动作风险级判定表

| 动作风险级 | 判定标准 | 是否需确认 | 审计 | 幂等键 | 失败处理 |
|---|---|---|---|---|---|
| **L0** | 纯导航 / 只读 / 无副作用 | 否 | 记录 | 不需要 | 显示错误提示，不阻断 |
| **L1** | 一般写操作（写本地库、改设置、导出产物） | **是** | 记录 | **需要** | 取消 → 不执行；失败 → 回滚 + 提示 |
| **L2** | 高风险（删除、清空投递箱、批量重算、导出含敏感数据） | **是 + 二次校验** | 记录 + **审计事件** | **需要** | 取消 → 不执行；失败 → 自动回滚 + 审计记 `failed` |

> `[已定]` `01-架构设计.md` §5.4：L0/L1/L2 **全部记录**；**写操作**（L1/L2）带 `Idempotency-Key`；**L2 需二次校验 + 失败回滚**；**删除类操作走回收站而非物理删除**。

> **[已定·重要] 导航与只读刷新必须显式声明为 L0，不得依赖缺省兜底。**
> 旧版协议层把**缺失**的 `risk` 兜底成 L1，导致「刷新」「切换情景」每次都弹确认框——这是必须避免的回归。
> 因此 `ActionRegistry` 中每个具名动作都必须**显式**写明 `risk`；未写明的动作在注册时校验失败（不进入 registry），而不是在运行时被兜底。
> `strongerRisk` 的 `?? ActionRisk.l1` 缺省**只用于防御性兜底**，正常路径不应命中。

### 5.2 「取更强风险」的实现

```dart
// lib/genui/actions/action_dispatcher.dart
const Map<ActionRisk, int> _riskOrder = {ActionRisk.l0: 0, ActionRisk.l1: 1, ActionRisk.l2: 2};

ActionRisk strongerRisk(ActionRisk? a, ActionRisk? b) {
  final left  = a ?? ActionRisk.l1;   // 缺省按 L1 处理（保守）
  final right = b ?? ActionRisk.l1;
  return _riskOrder[left] >= _riskOrder[right] ? left : right;
}
```

**声明来源**（两处，取更强）：

| 声明处 | 字段 | 说明 |
|---|---|---|
| A2UI 组件声明 | `CatalogItem.action.risk`（`lib/genui/catalog/`） | 组件 catalog 中为每个可点击组件登记的风险级 |
| 本地动作注册表 | `ActionRegistry[actionId].risk`（`lib/genui/actions/`） | 应用侧白名单动作的权威风险级（**白名单是安全边界**：未登记动作一律拒绝并告警） |

**最终生效风险级** = `strongerRisk(组件声明, 注册表声明)`。

**fail-closed** `[已定]`：

```dart
if (effectiveRisk != ActionRisk.l0) {
  final confirmer = options.confirm;         // 必须存在
  if (confirmer == null) {
    auditSink.record(AuditEvent(actionId: id, risk: effectiveRisk, outcome: 'rejectedMissingConfirmer'));
    return const DispatchResult.rejected(reason: '缺少确认处理器');  // 拒绝执行，不降级为 L0
  }
  ...
}
```

即：**缺确认处理器 → 拒绝执行**，绝不降级放行。这是基线 §7.1 的直接落地。

### 5.3 纯客户端下的动作分类

纯客户端（基线 §2）意味着**没有服务端副作用**。所有动作只能是「本地副作用」或「仅 UI 导航」两类。动作种类与风险级沿用 `04-动态UI与Agent-Native设计.md` §6.2：

| 动作 id | 种类 | 说明 | 类型 | 风险级 | 本地副作用 | 回滚 |
|---|---|---|---|---|---|---|
| `nav.open-surface` | `navigate` | 打开某个 surface（证据详情、trace 时间线） | 仅 UI 导航 | **L0** | 无 | — |
| `evidence.expand` | `navigate` | 展开一条证据的原文片段 | 仅 UI 导航 | **L0** | 无 | — |

> `[已定]` 组件动作**不得**直接调用工具或写库，必须经 `ActionDispatcher`；动作参数**不得**携带可执行代码或表达式，只允许声明式参数。

### 5.4 幂等 + 可回滚 + 审计（本地执行三件套）

```dart
// lib/genui/actions/action_ledger.dart
final class ActionLedgerEntry {
  final String idempotencyKey;   // PK；写操作的 Idempotency-Key（UUID）
  final String actionId;
  final ActionRisk risk;
  final String runId;
  final String payloadHash;       // 参数指纹；同 key 不同 hash → 视为冲突，拒绝执行
  final String outcome;           // pending | succeeded | failed | rejected | rolledBack
  final String? resultRef;        // 产物引用（文件路径 / 行主键）
  final String? undoDescriptor;   // JSON：逆操作描述
  final DateTime createdAt;
  final DateTime? handledAt;
}
```

**幂等** `[已定]`（基线 §7.4）：

1. 写操作携带 `Idempotency-Key`（UUID）；本地以键去重。
2. 执行前查 `ActionLedgerEntry`：
   - 存在、`payloadHash` 相同、`outcome == succeeded` → **直接返回上次结果**，不重复执行；
   - 存在、`payloadHash` 不同 → **拒绝执行**（键碰撞/参数漂移），记 `rejected`；
   - 不存在 → 插入 `pending` 行 → 执行 → 更新终态。
3. `pending` 行若在启动时被发现（上次进程崩溃）→ 标 `failed` 并按 `undoDescriptor` 尝试回滚。

**可回滚** `[已定]`：

| 动作类型 | `undoDescriptor` |
|---|---|
| 新增文件 | `{"type":"deleteFile","path":"..."}` |
| 新增行 | `{"type":"deleteRows","table":"...","pk":[...]}` |
| 覆盖写（重抓 / 重算） | 执行前落快照，`{"type":"restoreSnapshot","ref":"..."}` |
| 删除（物理删） | 执行前落快照，`{"type":"restoreSnapshot","ref":"..."}` |
| 删除（移入回收站） | `{"type":"restoreFromRecycleBin","ref":"..."}` |
| 配置变更 | `{"type":"restoreConfig","key":"...","valueRef":"..."}` |

`ActionDispatcher.rollback(actionId)` 执行逆操作，并把账本行标 `rolledBack`。

**审计** `[已定]`：

| 事件 | 落点 | 内容 |
|---|---|---|
| L2 动作发起 | `data/traces/<runId>.jsonl` | `step='ACT'`, `action='action_dispatch'`, `detail={actionId, risk, idempotencyKey, payloadHash}` |
| L2 动作完成 | 同上 | `action='action_result'`, `detail={outcome, resultRef, latencyMs}` |
| L2 动作回滚 | 同上 | `action='action_rollback'`, `detail={undoType}` |
| 全部动作 | `ActionLedgerEntry` | 完整记录，可查 |
| 缺确认处理器被拒 | 同 trace + 账本 | `outcome='rejectedMissingConfirmer'` |

> `[已定]` 基线 §7.1 要求 L2 需审计；本文把**全部动作**都写账本，L0/L1 **不写 trace 审计事件**（避免 trace 噪声）。这是对基线的超集，不违反基线。

## 6. 成本与预算（`J = L + μ·C`）

### 6.1 成本模型

基线 §7.7：`J = L + μ·C`（token 成本 + μ×协调成本）。

```dart
// lib/agents/budget/cost_model.dart
final class CostModel {
  final double costPerToolCall;     // 旧 app.yaml: cost_per_tool_call
  final double costPer1kTokens;      // 旧 app.yaml: cost_per_1k_tokens
  final double costPerLatencyMs;     // 旧 app.yaml: cost_per_latency_ms
  final double coordinationWeightMu; // 旧 app.yaml: coordination_weight_mu

  /// L：语言/推理成本
  double languageCost(TokenUsage u) => (u.total / 1000.0) * costPer1kTokens;

  /// C：协调成本（工具调用 + 等待）
  double coordinationCost({required int toolCalls, required int latencyMs}) =>
      toolCalls * costPerToolCall + latencyMs * costPerLatencyMs;

  /// J = L + μ·C
  double jointCost({required TokenUsage tokens, required int toolCalls,
                    required int latencyMs}) {
    final l = languageCost(tokens);
    final c = coordinationCost(toolCalls: toolCalls, latencyMs: latencyMs);
    return l + coordinationWeightMu * c;
  }
}
```

**为什么这样切分** `[已定·本文]`：

- `L` 随**产出长度**增长，是"能力成本"；
- `C` 随**协作动作数量与等待时间**增长，是"多 agent 税"；
- `μ` 是把两者放到同一量纲的换算权重，用于**跨模式对比**：协同模式多花的是 `C`，所以协同是否值得，取决于协同带来的决策质量提升是否超过 `μ·C`。这正是论文 P3 的核心论点。

**配置来源** `[已定]`：旧 `configs/app.yaml` 的 `orchestration` 段（`cost_per_tool_call: 0.001`、`cost_per_1k_tokens: 0.001`、`cost_per_latency_ms: 0.00001`、`coordination_weight_mu: 0.1`），迁到 `configs/app.json` 的同名键。

> `[建议·待复核]` 是否区分 prompt / completion token 计价（DeepSeek 二者单价不同）。旧配置只有单一 `cost_per_1k_tokens`，本文按旧语义保留。

### 6.2 硬预算与熔断

```dart
// lib/agents/budget/budget_guard.dart
final class RoleBudget {
  final int maxToolCalls;      // 旧: max_tool_calls_per_agent = 6
  final int maxTokens;         // 旧: max_tokens_per_agent = 4000
  final int maxLatencyMs;      // [建议·待复核] 默认 120000
}

final class TaskBudget {
  final RoleBudget perRole;
  final int maxTotalToolCalls;  // = 主体任务数 × perRole.maxToolCalls
  final int maxTotalTokens;     // = 主体任务数 × perRole.maxTokens
  final int maxWallClockMs;     // 整轮上限
  final int maxDelegations;     // = 3（§3.3）
  final double maxJointCost;   // J 的硬上限；null 表示不限
}
```

**扣减与截断规则** `[已定·本文]`（继承旧 `budget.py` 语义）：

| 事件 | 扣减 | 超限行为 |
|---|---|---|
| 角色调用工具 | 该角色 `toolCalls +1` | 超过 `maxToolCalls` → **拒绝该次工具调用**，记 `budget_exceeded` |
| 角色消耗 token | 该角色 `tokens += used` | 超过 `maxTokens` → **截断**（按上限计），记 `budget_exceeded`，`truncated=true` |
| 交叉验证 / 互评调用 | 计入**执行者角色**的 token 池 | 同上 |
| 合成调用 | 计入**整轮总池** | 同上 |
| 委派次数 | 任务级 `delegations +1` | 超过 `maxDelegations` → 中间件拒绝，编排层降级为「按既定角色集合直接调用」 |
| `J` 超 `maxJointCost` | — | **熔断**：停止后续非必要 LLM 调用 |

**熔断器** `[已定·本文]`：

```dart
final class CircuitBreaker {
  bool tripped = false;
  String? reason;
  // 触发条件（任一）：
  //  1) elapsed > taskBudget.maxWallClockMs
  //  2) jointCost > taskBudget.maxJointCost
  //  3) 连续 N 次角色失败（N=2）[建议·待复核]
  // 触发后：后续 generate() 调用不再执行，编排层显式报错并写 trace
}
```

熔断必须写 trace：`action='budget_exceeded'`，`detail={reason, elapsedMs, jointCost}`，并在最终卡上标注「本次研判因预算/时间限制提前收敛」。

> `[已定]` 预算超限**不阻塞**最终卡输出（旧语义 `budget_exceeded → record`），但必须在最终卡的「局限」中可见。

### 6.3 预算一致性（消融可比性的前提）

`[已定]` 三种模式的**每角色**预算必须一致（6 次工具调用 / 4000 tokens）。一次 run 总预算 = **承担的主体任务数** × 每角色上限。

| 模式 | 承担的主体任务数 | 每角色上限 | 一次 run 总上限（工具/tokens） |
|---|---|---|---|
| single | 3（1 个通用 agent 依次承担三主体任务） | 6 / 4000 | 18 / 12000 |
| independent | 3 | 6 / 4000 | 18 / 12000 |
| collaborative | 3 | 6 / 4000 | 18 / 12000 |

> 协同模式的交叉验证与仲裁工具调用**从执行者角色的预算中扣减**，因此协同模式实际可用预算少于独立模式——这是真实成本差异，应体现在 `J` 上，而不是被预算对齐掩盖。

## 7. 人在环（HITL）

### 7.1 触发点清单

| # | 触发点 | `HitlItem.kind` | 是否阻塞最终卡 | 自动策略（无人在线时） |
|---|---|---|---|---|
| 1 | 存在未解决的事实/方向冲突 | `unresolvedConflict` | 否（保留冲突并标记「需人工复核」） | `escalate` |
| 2 | 核验器发现 error 级问题 | `verificationFailure` | 否（相关 claim 不进入建议） | `escalate` |
| 3 | 角色越权（工具或信息域） | `permissionViolation` | 否 | `escalate` |
| 4 | 任一角色或共享信号为 `critical` | `highRisk` | 否 | `escalate` |
| 5 | L2 动作待执行 | `actionApproval` | **是**（动作层） | `escalate`（不自动执行） |
| 6 | 预算/时间超限 | `budgetExceeded` | 否 | `record`（仅记录） |

> `[已定·本文]` 旧 `HITLKind` 的五个取值全部保留；新增 `actionApproval` 承载 L2 动作审批（旧系统里 L2 审批在渲染层 `confirm()`，本文统一到 HITL 队列以便审计一致）。

### 7.2 交互形态（A2UI 确认卡）

HITL 在 UI 上是一个**独立 surface**，通过 `updateComponents` / `updateDataModel` 更新状态，**不阻塞对话流**。

```
surfaceId = "cbr.hitl.<itemId>"
rootId    = "hitl-root"

createSurface {
  surfaceId, rootId,
  components: [
    { id: "hdr", kind: "Text",            props: { text: "需要人工确认：<kind 中文名>" } },
    { id: "ttl", kind: "Text",            props: { text: "<item.summary>" } },
    { id: "ctx", kind: "ConflictDiff",    props: { items: [ /* 双方 claim / 风险级 / 证据 id */ ] } },
    { id: "why", kind: "Text",            props: { text: "<裁决失败原因>" } },
    { id: "evd", kind: "EvidenceList",    props: { items: [ /* 证据列表，含 source.releaseTime */ ] } },
    { id: "act", kind: "ConfirmCard",     props: {
        itemId, kind, risk: "L1"|"L2",
        options: [
          { id: "approve",  label: "确认维持",       risk: "L1" },
          { id: "reject",   label: "驳回相关结论",   risk: "L1" },
          { id: "override", label: "按人工结论替换", risk: "L2" }   // override 需二次确认
        ],
        timeoutSeconds: 300,
        onTimeout: "escalate"
    } }
  ]
}
```

> `[已定]` `ConfirmCard` 的**动作风险级（L0/L1/L2）与风险等级（low/medium/high/critical）是两件事**，界面措辞必须分离（`04` §5.2 / `08` §9）。

**动作分级** `[已定·本文]`：

| 动作 | 风险级 | 副作用 | 审计 |
|---|---|---|---|
| `approve`（确认维持） | L1 | 更新 `HitlItem.status='approved'`，写 trace | 账本 + trace |
| `reject`（驳回） | L1 | 相关 claim 标 `rejected`，从最终建议剔除 | 账本 + trace |
| `override`（人工替换） | **L2** | 写入人工结论 + 原文，写 trace | 账本 + trace + 标记「人工结论，非模型证据」 |
| `escalate`（无人在线） | L0（仅标记） | `status='autoProcessed'`，`needsHumanReview=true` | trace |

> **override 的诚实性约束** `[已定]`：人工替换的内容**不得**被当作模型证据。它在 `DecisionCard` 中以 `source='human'` 标注，单列在 `humanOverrides` 字段（**不进 `evidenceIds`**），并出现在最终建议的显著位置。

### 7.3 超时 / 取消 / 拒绝

| 情形 | 行为 | 状态流转 |
|---|---|---|
| **超时**（默认 300 秒） | 按 `onTimeout='escalate'`：保留未决项、标记「需人工复核」、不阻塞流程 | `pending → autoProcessed(escalate)` |
| **用户取消**（关闭确认卡） | 等价于弱 `reject`：标记 `cancelled`，相关结论**保留但不计入最终建议的强断言** | `pending → autoProcessed(cancelled)` |
| **用户拒绝** | 明确驳回：相关 claim `status='rejected'`，从最终建议剔除，在「局限」中说明 | `pending → rejected` |
| **用户离线/应用退出** | 启动时扫描 `pending` 项：按 `autoPolicies` 处理并写 trace | `pending → autoProcessed` |
| **重复处置** | 已终结项再操作 → 拒绝并提示，不改状态 | 保持原状态 |

> `[已定]` HITL 处置动作**永不**静默生效：每次 `approve/reject/override` 都写 trace，即使审计写入失败也不影响主流程（旧语义：审计失败不阻断）。

## 9. 失败模式与降级

> **绝对禁止**：任何失败路径都不得静默降级为 mock / 伪造数据 / 占位数值（基线 §4、§7.6、§7.10；迁移清单第 29 条：LLM 失败**必须失败退出**，不得用规则模板冒充模型结论）。下表"允许的降级"全部是**减少结论**，不是**编造结论**。

### 9.1 五类失败与策略

| 失败 | 检测点 | 立即动作 | 允许的降级 | 禁止 |
|---|---|---|---|---|
| **模型超时** | `ai.generate()` 超时（`AgentInput.deadline`） | 重试 ≤ 2 次，指数退避 | 仍失败 → 该角色 `status=timeout`，**不产出卡片**；最终卡列出缺席角色并写 `limitations` | 不得用 mock 输出填充；不得用规则模板生成卡片；不得用其他角色的结论冒充该角色 |
| **工具失败** | `ToolResult.ok == false` 或抛异常 | 记 `tool_call{ok:false, error}`；不产生 `Evidence` | 相关 claim 被自检回填丢弃并记 `claim_rejected`；`limitations` 记「工具 X 不可用」 | 不得用估算值/历史值/行业均值代替 |
| **部分角色失败** | `AgentOutput.status != ok` | 其余角色继续 | 最终卡列出缺席角色（`degradedRoles`）；`finalLevel` 不采用缺席角色；合成文本显式说明缺口 | 不得静默少一个角色；不得把缺席当正常 |
| **上下文超限** | 累计 token 触达 `maxTokens` | 分层裁剪（顺序见 §9.2） | 裁剪后仍超限 → 截断该角色 LLM 输出并标 `truncated=true` | **不得**先丢证据绑定再保留 claim |
| **凭证缺失** | DeepSeek key 未配置 / 401 | 抛 `LlmAuthFailure`，UI 引导到设置页 | LLM 角色**全部不可用**；但**确定性工具链仍可用**：可展示行情/工具读数与「数据概览」surface | **不得**切到 mock；不得用旧缓存结论冒充本次实时研判 |
| **JEV 不可用** | `judge_availability()` 返回不可用 | 回退**规则门卫** | 规则门卫**不产出置信度**，在 `note` 明说「未使用模型判断」 | 不得把规则门卫结果伪装成模型判断 |

### 9.2 上下文裁剪的优先级表

`[已定·本文]` 当角色 prompt 超预算，按此顺序裁：

| 优先级 | 裁剪对象 | 保留规则 |
|---|---|---|
| 1 | `peerFacts` 中未被本次复核引用的证据 | 保留被复核的 ≤2 条 |
| 2 | 工具证据 `payload` 中的非标量/大字段 | 保留 `value` / `unit` / `title` / `tool.inputsHash` |
| 3 | 知识库证据的 `summary` 全文 | 保留 `chunkId` + 首句 + `releaseTime` |
| 4 | `limitations` 去重 | 保留全部语义去重后条目 |
| 5 | **任何情况下不裁** | `evidenceIds` 与 `value`/`unit` 的绑定关系、`asOf`、角色阈值 |

### 9.3 降级的可见性契约

`[已定]` 任何一次降级都必须同时出现在三处，缺一即为实现缺陷：

1. **trace**（`analysis_done{status}` 或 `tool_call{ok:false}`）；
2. **最终卡 `limitations`**；
3. **UI 上的降级标记**（角色卡角标「降级」+ 悬浮说明降级原因）。

## 10. 与动态 UI（A2UI）的接口

> 协议细节、catalog 组件集与动作模型见 [`04-动态UI与Agent-Native设计.md`](04-动态UI与Agent-Native设计.md) 与 [`06-设计系统与美学规范.md`](06-设计系统与美学规范.md) §9。本节定义**编排阶段 → A2UI 内容**的对应关系与责任边界。
> `[已定]` ADR-002：**`lib/genui/adapter/` 是唯一允许 `import 'package:genui/...'` 的目录**；catalog 是安全边界，`validate: 'strict'`。

### 10.1 阶段 → A2UI 产物对照

> `[已定]`（`04` §4.3 / §7）：**一次研判 = 一个 surface**（`surfaceId` + `rootId`）；组件树是邻接表结构 `{id, kind, children[], props}`；数值更新走 `updateDataModel` 只 patch 数值，不重绘树；**不先渲染半成品 surface**。

| 阶段 | 产物类型 | A2UI 消息 | 组件 id（catalog 内，`basic` + `cbr.basic`） | 落到 surface 的哪个子树 |
|---|---|---|---|---|
| R0.0 意图路由 | **消息**（对话流文本） | 无（纯文本 part） | — | — |
| R0.0 澄清 | **消息** | 无 | — | — |
| R0.1 检索 | surface 子树（数据概览） | `createSurface`（首个 surface 一次性创建） | `DataCardList`, `MetricTable` | `data` |
| R0.2 角色产出 | surface 子树 × 3（角色研判卡） | `updateComponents` | `RoleCard`, `MetricTable`, `ClaimTable`, `EvidenceList` | `roles.<role>` |
| R1 证据共享 | surface 子树（证据黑板） | `updateComponents` | `EvidenceList` | `blackboard` |
| R2 交叉验证 | surface 子树（复核结果） | `updateComponents` | `CrossValidationList` | `crossCheck` |
| R3 分歧识别 | surface 子树（分歧对照） | `updateComponents` | `ConflictDiff` | `conflicts` |
| R4 仲裁 | 更新既有子树 | `updateComponents` + `updateDataModel` | `ConflictDiff`（状态更新） | `conflicts` |
| R5.1 核验 | surface 子树（核验报告） | `updateComponents` | `VerificationSummary` | `verification` |
| R5.2 合成 | surface 子树（最终结论） | `updateComponents` | `DecisionSummary`, `RoleCard`（只读摘要）, `CostMeter` | `summary` |
| R5.3 HITL | **独立 surface**（确认卡） | `createSurface` | `ConfirmCard`, `ConflictDiff`, `EvidenceList` | `surfaceId = cbr.hitl.<itemId>` |
| R5.4 渲染 | 更新 | `updateComponents` / `updateDataModel` | 全部 | — |
| （全流程） | 数据不可得态 | `updateComponents` | `AccessRequired` | **绝不出现 0 / `--` / `N/A`**，只写来源 + 原因 + 单一主动作 |

**HITL 确认为何独立成 surface** `[建议·待复核]`：`04` 规定「一次研判 = 一个 surface」，但 HITL 确认卡是需要用户回应的**独立交互单元**，且可能在研判结束后很久才被触发（超时/离线后回到应用）。因此本文建议 HITL 用**独立 surface**（`cbr.hitl.<itemId>`），与主研判 surface 解耦；如 Lead 决定统一为单 surface，则需接受「未触发 HITL 时该子树为空」的复杂度。**此条不影响其它语义。**

**「消息」与「surface」的判别规则** `[已定·本文]`：

- **消息**：一句话即可表达、不含结构化数据、无需用户交互 → 走对话流文本 part（如「已按 2026-08-05 时点、协同模式重新研判」）。
- **surface**：含表格/列表/可点击动作、需要独立滚动与状态更新 → 建 surface。
- 判不准时**倾向 surface**：surface 可被引用、可被链接、可回看；消息不能。

### 10.2 Catalog 的责任边界

`[已定]` 基线 §3 风险 3 + ADR-002 + `04` §5：所有 Agent→UI 的调用**必须经我方自有 catalog 封装层**，不得让模型直接输出未登记组件。

```
Agent / 编排层
   │  只能产出「领域对象」（RiskCard / Claim / Evidence / Conflict / Cost / Gate）
   │  不产出任何 UI 指令
   ▼
lib/genui/adapter/surface_bridge.dart → SurfaceBridge
   │  ├ 组件映射（领域对象 → catalog 组件 kind）
   │  ├ CbrVisualGuard（组件名 / 参数名 / 颜色 / 图标白名单）
   │  ├ 文案校验（08 §9 T-1~T-10）
   │  └ → A2UI createSurface / updateComponents / updateDataModel
   ▼
genui SurfaceController + Conversation + A2uiTransportAdapter
```

**因此**：模型**不直接生成 A2UI 消息**。模型生成的是领域对象；`SurfaceBridge` 负责映射成 catalog 组件，`CbrVisualGuard` 负责拦截越界的组件名/参数。

> `[已定]` A2UI 协议版本 `v0.9`；catalog 组件集 = **`basic`（通用）+ `cbr.basic`（CBR 领域）**，真源 `lib/genui/catalog/catalog_components.json`（`04` §5.1）；校验模式 `strict`；`catalog_version` 独立于协议版本（VC-6）。
>
> `[已定]` catalog 组件**必须是 `lib/ui/components/` 的同一份 widget 实现**，不得为 Agent 另写一套皮肤或简化版（VC-1）；组件必须实现 loading / empty / error / disabled / 无权限**全套状态**（VC-3）。
>
> `[已定·重要]` **`RiskBadge`（风险等级徽章）与动作风险级徽章分离**——`low/medium/high/critical` 是风险等级，`L0/L1/L2` 是动作风险级，界面措辞必须分离（`04` §5.2 / `08` §9）。

### 10.3 渲染失败的降级

| 失败 | 处理 | 用户看到 |
|---|---|---|
| 组件未登记 | `CbrVisualGuard` 拒绝该 surface | `renderError{surfaceId}` + **纯文本摘要（不含任何未经核验的数值）** |
| `strict` 校验失败 | 拒绝该 surface | 同上 |
| 参数越界（颜色/字号等） | 丢弃该参数 + 记 trace | 正常渲染，参数取默认值 |
| 图标不在白名单 | 替换为默认图标 + 记 trace | 正常渲染 |
| 整个 R5.4 失败 | 对话流追加纯文本摘要 | 「界面渲染异常，详见审计记录」 |
| 协议版本不匹配 | 明确报错 | 「前端与后端协议版本不匹配」+ 版本号 |

**硬规则** `[已定]`（`04` §8）：① **不得**用未校验内容渲染；② **不得**抛异常中断整个会话；③ 渲染期异常由**块级错误边界**兜底，该区块错误态，其余区块不受影响。

## 12. 与本文相关的未决项

| # | 未决项 | 本文暂定 | 影响 |
|---|---|---|---|
| 1 | `maxDelegations=3` / `artifactStrategy='session'` 的具体取值 | 建议值 | 消融的协作预算口径 |

| 6 | 人工 override 的结论是否进入 `evidenceIds` | **不进入**，单列 `humanOverrides` | 证据链纯度 |
| 7 | JEV 三处「已实现未接入」能力（冲突三分类 / 语义核验 / 证据重排）本代是否启用 | 建议启用语义核验，冲突三分类作为扩展点 | 核验准确率 |
