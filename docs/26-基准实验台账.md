## 2. 跑批中发现的实现缺陷（都会让结论失真）

| # | 缺陷 | 后果 | 处理 |
|---|---|---|---|
| E1 | `roles.json` 的 `max_tokens_per_agent=4000` 低于真实消耗（每角色 5–6.4k） | `chargeTokens` 每次截断 → `truncated=true` → **所有 run 的 `partial` 恒为 true**，且 token 记账被压到 4000/角色（协同臂真实约 22k，只记 16459） | 提到 16000；`max_wall_clock_ms` 300s → 900s（单时点实测 100–120s，300s 在多角色重试时会熔断） |
| E2 | `bench_console` 的分片校验放在切分之后 | 分片永远报「可评分时点不足」，四片全灭 | 校验移到切分之前，分片为空单独报错 |
| E3 | `max_tokens=4000`（生成侧） | 推理型模型先烧 reasoning token，JSON 被截断 → 角色 `failed` | 默认 8000 |
| E4 | FTS 索引不随写入更新 | 无向量时 `memory.search` 静默返回空 | 写入后 `optimize(Index)` 增量重建 + 回归测试 |
| E5 | jieba tokenizer 需要外部词典文件 | 缺文件时静默退化为 simple（中文查不到） | 改用内置 ICU 分词；`memory.stats.fts_tokenizer` 如实暴露 |

> E1 是在第一批 36 个时点跑完后发现的。该批数据的 `partial_rate=1.000`，
> 不能作为最终结论，已整批丢弃重跑（旧产物未入库）。
