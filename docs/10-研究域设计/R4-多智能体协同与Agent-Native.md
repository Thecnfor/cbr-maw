## 1. 研究命题：为什么跨境金融风险适合「多智能体 + Agent-Native」

### 1.1 问题的结构特性

跨境金融风险预警与一般的文本分类/预测任务有四个结构性差异，这四点共同构成"多智能体是合适载体"的论证基础：

| # | 结构特性 | 事实依据 | 对架构的含义 |
|---|---|---|---|
| **S1** | **同一压力事件对不同主体有不同且都"正确"的含义** | 旧系统三角色阈值互不相同（`high_stress_prob`：regulator 0.50 / investor 0.45 / financing 0.40，见 `configs/roles.yaml`）；决策损失权重亦异（漏报 5.0 vs 尾部损失 5.0 vs 流动性缺口 5.0） | **必须**有多个持不同目标函数的分析单元，而不是一个"更聪明的"单模型 |
| **S2** | **结论是「证据 + 口径 + 时点」的复合体，不是标量** | 旧 `Evidence` 必须带 `tool.version`、`inputs_hash`、`release_time`；`claim` 必须绑定 `evidence_ids`（`ref/contracts/schemas.py`） | 分析单元必须能**产出可审计工件**，而不是只吐一段文本 |
| **S3** | **协同过程本身就是研究对象** | 旧系统已实现 R0–R5 五阶段协同与冲突仲裁，并显式区分 `fact`/`directional`/`preference` 三类冲突 | 协同必须**可配置、可开关、可消融**，否则无法证明"协同有用" |
| **S4** | **结论的使用者是三类不同专业角色，且会采取行动** | 监管关注建议 / 组合风险预算 / 融资安排；三类使用者需要不同的界面粒度与不同的确认强度 | 界面必须**由 Agent 按使用者意图生成**，且动作必须带风险分级与人在环 |

### 1.2 论证链：为什么不是"更好的单模型"或"固定仪表盘"

| 替代方案 | 为什么不够 | 本文架构如何回应 |
|---|---|---|
| **单一 LLM + 单一提示** | S1：一个目标函数无法同时优化漏报与误报成本；旧系统的 `single` 模式正是这个基线 | 角色 × 目标函数 × 阈值 × 损失权重**全部配置化**，冲突被显式建模而非被平均掉 |
| **纯数值融合模型（无 LLM）** | 只能给标量压力概率，无法解释驱动因子、无法给主体差异化建议、无法承接"口径 + 时点"证据链 | 旧 `E0` 基线保留为对照；融合信号作为 `kind=signal` 证据进入证据包，与工具证据并列 |
| **固定页面仪表盘（旧 SDUI 路线）** | 界面由服务端固定 spec 推送，**不随 agent 行为变化**，因此界面是常量、不可消融；也无法按三类使用者切换呈现粒度 | Agent-Native：界面由本地 Agent 在对话流中生成，**呈现本身成为可控自变量**（§3.6 E26） |
| **人在环作为最后一道审批** | HITL 若只做"批准/驳回"，则人类只承担签字，不参与消融对照 | HITL 的**触发点集合本身可消融**（§3.6 E28），可测量"人在环到底带来多少" |

### 1.3 为什么必须是 Agent-Native（而不是只把 SDUI 换皮）

| 维度 | 旧 SDUI | Agent-Native（A2UI + genui） | 对研究的意义 |
|---|---|---|---|
| 界面来源 | 服务端推 `AppManifest`/`PageSpec`（`ref/docs/architecture/adr-2026-10-22-single-frontend-sdui.md`） | 本地 Agent 在对话流中生成 A2UI 消息 | 界面与 agent 行为**耦合** → 可做呈现层消融（E26） |
| 交互粒度 | 页面级、manifest 白名单动作 | 组件级、catalog 封装层 + 动作风险级 L0/L1/L2 | 可研究"呈现粒度 → 人工确认行为"的关系 |
| 部署形态 | 需要 BFF + 前端服务 | 纯客户端单进程（基线 §2） | 研究装置可**被第三方完整复现**，无需部署 |
| 可观测性 | 后端 trace + SSE | 本地 trace（JSONL）+ 本地状态机 | 研判链路可**逐条回看**，成为论文的定性材料 |
| 安全边界 | manifest 动作白名单 | **catalog 封装层**（模型不得直接输出未登记组件）+ 动作风险级 + fail-closed | 既是安全设计，也是"Agent 驱动的 UI 是否可控"的研究问题 |

### 1.4 核心假设（可证伪）

> 每个假设都写成**可被某个消融否证**的形式，并指明否证所需的对照与指标。

| ID | 假设 | 若为真，应观察到 | 若被否证，证据形态 |
|---|---|---|---|
| **H1（角色专业化）** | 三类主体的目标函数/阈值/损失权重差异带来**优于伪分工**的决策质量 | `E9`（完整协同）在 `decision_loss` 上优于 `E8`（伪分工：三角色同 prompt 同权限），且差异在显著性检验下成立 | E8 与 E9 的差异 CI 跨 0 |
| **H2（协同增益）** | 证据共享 + 交叉验证 + 冲突协调三件套**各自**有正贡献 | `E9` > `E6`（仅共享）> `E5`（无协同）；且 `E10`/`E11`（分别去掉交叉验证 / 冲突协调）都劣于 `E9` | E9 与 E10/E11 无显著差异 → 相应机制无效 |
| **H3（证据链价值）** | 强制"结论必须绑定证据 + 数值必须可回指"显著降低无依据断言 | `E4`（单智能体 + 工具 + 知识库）在 `unsupported_claim_rate` / `numeric_error_rate` 上优于 `E2`（单智能体无工具无知识库） | 无差异，或 E4 反而更差 |
| **H4（成本可解释性）** | 协同带来的决策质量增益**能够覆盖**其协调成本 `μ·C` | 在 `J = L + μ·C` 口径下，E9 的 `J` 增量小于其决策损失的下降量 | `μ` 需上调到极大值 E9 才划算 → 协同不经济 |
| **H5（Agent-Native 界面的价值）** | 由 Agent 按使用者角色生成的界面，比固定界面**降低人工确认成本并提高核对准确率** | E26（Agent 生成 surface）相对 E26-fixed（固定 surface）的 `HITL 确认耗时`、`evidence_accuracy`（人工侧）更优 | 无差异 → Agent-Native 只增加复杂度，不增加价值 |
| **H6（模态互补）** | 文本模态在数值模态之外有**增量预测力** | R1 方向：Numeric+Text 相对 Numeric-only 的 `pr_auc` / `recall_at_top_decile` 提升且 CI 不跨 0 | 无提升 → 文本模态在当前语料下无增量 |

> **H6 的现实预期**：旧项目已在其架构文档中记录「真实数据 P1 中数值-only 判别力较强，而**文本模态增益不显著**，需更均衡的语料或更强文本表征再验证」（`ref/docs/architecture/CBR-MAW_architecture_v1.md`）。因此 **H6 在本代被标为"待重新检验"而非"已成立"**；若复现不显著，必须如实报告（§7 C3）。

## 2. 四个研究方向的接线

### 2.1 总览：方向 → 智能体 → 工具 → 证据 → 消融轴

| 方向 | 主要产出物 | 落到哪个智能体 | 通过什么工具进入 | 证据 kind | 可消融的轴 |
|---|---|---|---|---|---|
| R1 MediaTone | Media Tone / Positive Tone / Negative Tone 三指标 | 三角色共享（作为外生解释变量） | `forecast`（把 tone 作为特征注入融合预测）+ `knowledge_search`（检索相关报道） | `signal`（`payload.modality_contrib['text']`） | 模态轴（E0/E1） |
| R2 多模态情感 / 跨模态对齐 | 文本+语音(+图像/视频) 的对齐与融合；模态缺失鲁棒 | 三角色共享 | `risk_measure`（融合信号）+ 未来的多模态推理插件位 | `signal` | 模态轴（7 组组合） |
| R3 时空分析 | 夜光/遥感作为经营活动空间代理；事件扩散空间因果 | 主要落在 **investor** 与 **regulator**（外溢判断） | `systemic_risk`（跨市场外溢）+ 未来的时空工具 | `tool`（若落地为确定性工具）或 `signal` | 模态轴（新增 spatial 开关） |
| **R4（本方向）** | 角色分工、冲突消解、证据链核验、人在环、审计 trace | **全部四身份** | 全部工具 + 委派中间件 | `tool`/`kb`/`signal`/`market`/`policy` | 角色轴 / 协作轴 / 呈现轴 / HITL 轴 |
| **R4（门卫侧）** | JEV 裁判的**封闭选项**判断：准入、语义支持判定、冲突三分类、证据重排 | 门卫（`lib/agents/gate/`，**非生成者**） | `knowledge_search`（重排用） | 不产出新证据 | 门卫轴（E30） |

### 2.2 R1 MediaTone 如何接入

```
R1 产出（研究侧）                    agent 架构侧（工程侧）
─────────────────────                ───────────────────────
MediaTone 三指标                →   RiskSignal.payload / modality_contrib
  (日频、as_of 对齐)                 作为 kind=signal 证据注入证据包
  ↓
双轨打分（Cloud 情绪 API vs 词典法）→  两轨的差异本身成为一个 signal 分量
  ↓                                         「打分法差异大」= 情绪读数不稳定
增量信息检验                              → forecast 工具的输入特征
  (相对数值变量的增量预测力)                  E0 vs E1 回答它
```

**接线点（工程）**：

| 接线点 | 内容 |
|---|---|
| 特征层 | `RiskSignal` 增加 `mediaTone{media, positive, negative}` 字段，随 `as_of` 一起切片；`modality_contrib` 中 `text` 分量即其贡献 |
| 证据层 | 融合信号以 `kind=signal` 进入黑板，`evidence_id` 形如 `ev_sig_<hash8>`，`source.releaseTime` = 当日发布时点 |
| 工具层 | `forecast` 工具的 `include_drivers=true` 时，`RiskDriver.factor` 中出现 `media_tone` 项；`systemic_risk` 的驱动归因同理 |
| 角色层 | **三角色共用**——MediaTone 是市场级外生变量，不属于任何单一主体的私有信息域；因此它不进入 `info_permissions` 白名单（避免与角色权限矩阵混淆），而是通过 `signal` 证据进入 |
| 消融层 | `modality.text = false` → `E0`；`modality.text = true` → `E1`；C-2 组可做三轨（数值 / 数值+文本 / 数值+文本+双轨差异） |

**研究侧要求**（属于 R1 文档，此处只列接口约束）：

- 三指标的**定义式、公式、经济含义**必须先补齐（基线 §5 明确指出旧项目这三列全空）；未补齐前，R1 只能作为**探索性**结果报告。
- 日度聚合规则（均值 / 加权 / 中位数）必须**先定后跑**，并在所有消融中保持不变（否则模态消融不可比）。

### 2.3 R2 多模态情感 / 跨模态对齐如何接入

| 层次 | R2 的工作 | 接入 agent 架构 |
|---|---|---|
| **模态对齐层** | 文本/语音/数值的时间对齐与跨模态对齐（`ref/参考文献/Cross-modal alignment and fusion/`） | 对齐后的多模态向量 → `RiskSignal` 的融合输入 → `kind=signal` 证据 |
| **模态缺失鲁棒** | 某模态缺失时的重建/插补（`ref/技术工具/技术or模型文献/模态缺失的情感分析.pdf`） | 缺失模态**必须显式标记**，不得用插补值冒充实测；证据 `payload.modalityPresent = {text:false, audio:false, numeric:true}` |
| **推理落地** | 图像/视频/语音推理 | 基线 §6 Q5：**本代先留采集与管线，推理留插件位**。因此 R2 在 agent 架构侧表现为**工具插槽位**，不是已实现能力 |

**接线点（工程）**：

| 接线点 | 内容 |
|---|---|
| 工具插槽 | `ToolRegistry` 中预留 `multimodal_infer`（名称待定），未启用时 `ToolRegistry.allow()` 对任何角色返回 `false` → **角色调用即越权**，被核验器记 `permission` 违规 |
| 证据层 | 多模态推理结果若接入，必须是 `kind=tool`（有版本、可重算、带 `inputsHash`）或 `kind=signal`；**不得**是模型自由文本 |
| 角色层 | 语音/图像证据进入证据包时，`evidence.source.releaseTime` 必须 ≤ `as_of`（C2） |
| 消融层 | 7 组模态组合（Numeric / Text / Audio / Numeric+Text / Numeric+Audio / Text+Audio / 全模态），每组对应 `ExperimentConfig.modality` 的一个布尔向量 |

**关键研究约束**：模态消融必须是**同一份代码路径、同一预算、同一窗口**下的开关切换（基线 §7.9），否则测到的是实现差异而不是模态贡献。

### 2.4 R3 时空分析如何接入

> R3 的完整设计见 [`R3-时空分析-夜光与遥感.md`](R3-时空分析-夜光与遥感.md)。本节只说**它如何进入 agent 架构**。R3 的消融编号占 `E13–E23`（见 §3.7 的编号空间分配）。

| 层次 | R3 的工作 | 接入 agent 架构 |
|---|---|---|
| **空间代理** | 夜光强度 / 遥感影像作为企业经营活动强度代理 | 产出为企业级/区域级的**外生特征** → 融合信号分量 → `kind=signal` |
| **时空内核** | 六维压力 → Gaussian HMM 状态机 → 事件语法 → **四/五视图历史类比 + 反例对照** → AW-LP 条件分位路径 | 作为 `forecast`（条件分位路径）与 `scenario`（类比情景）的**扩展输入**，或独立确定性工具（`analogy.retrieve` / `forecast.awlp` 等，命名见 R3 §5.3） |
| **空间因果** | 事件扩散的空间因果（如某地冲击的外溢路径） | 作为 `systemic_risk` 工具的**扩展输入**或新的确定性工具 `spatial_spillover`（名称待定） |
| **时点对齐** | 遥感/夜光有**采集周期与延迟**（周/月频） | 必须像日频行情一样声明 `release_lag_days` / `publish_hour` / `tz_offset`（基线 §4），否则构成 PIT 泄漏 |

**接线点（工程）**：

| 接线点 | 内容 |
|---|---|
| 数据层 | 新增序列进入 `SourceRegistry`，声明 `frequency`（weekly/monthly）与 `release_lag_days`；陈旧度按 `stale_threshold_days` / `monthly_stale_threshold_days` 判 |
| 工具层 | 若 R3 产出为确定性指标 → 做成 `kind=tool` 证据（可重算、带 `inputsHash`）；若为模型推断 → `kind=signal` 并附 `modelVersion` |
| 角色层 | 空间代理与"跨境资金流动"主题相邻，最可能先在 **investor**（组合暴露的空间集中度）与 **regulator**（外溢路径）上产生可解释差异；**financing** 角色暂不消费（避免越权扩展） |
| 消融层 | `ExperimentConfig.modality` 需扩展出 `spatial` 开关（默认 false）；R3 自身的 `E13–E23` 在同一实验框架内执行 |

**与 S1 的连接**：R3 天然制造**跨主体的差异化解读**（监管看外溢路径、投资看暴露集中、融资方无空间信息）→ 这是"偏好差异"而非"事实冲突"的天然来源，可用来检验 H1 与冲突分类器的正确性。

**跨域连接的一条强约束**：R3 的条件分位路径（AW-LP）必须在**扩展窗口样本外**（`p + h ≤ t`）下产生，且其评价口径（CRPS + DM 检验 + PIT 校准）与本文 §5.4 的 S10 一致——否则 R3 的结论与 R4 的结论无法放在同一张表里比较。

### 2.5 R4 自身如何接入（自指）

R4 的研究对象就是编排过程本身，因此它有四条"自指回路"：

| 回路 | 机制 | 产出 |
|---|---|---|
| **① 编排即被测对象** | `DecisionCard.coordination` + `CoordinationStats` + `Conflict[]` + `VerificationReport` 全量落盘 `data/traces/<runId>.jsonl` | 协同过程的**结构化记录**，可做过程指标统计（证据共享率、重复证据率、冲突率、升级率） |
| **② 界面是被测变量** | 同一 `DecisionCard` 可渲染成不同 surface 组合（E26） | 呈现层消融的结果 |
| **③ 人是被测变量** | HITL 触发点集合与超时策略可配置（E28） | 人工介入的**行为数据**（确认耗时、驳回率、覆盖类型分布） |
| **④ 裁判是被测变量** | JEV 门卫可用 / 不可用可配置（E30）；不可用时**规则门卫回退**且**不产出置信度** | 裁判对结论的影响（`uncertain` 比例、`claim_rejected` 比例） |

**门卫的诚实性约束** `[已定]`：JEV 是**裁判**不是生成者——只对已给定的问题做封闭选项判断（`noul` / `choice` / `score`），不产自由文本。JEV 不可用时必须回退规则门卫，规则门卫**不得产出置信度**，并明说「未使用模型判断」。`judge_availability()` **只查配置、不发网络请求**。

> **旧系统的缺口即本代的研究机会**：迁移清单第 59–61 条记录了 JEV 三处「已实现但未接入主链路」的能力——冲突三分类（`classify_conflict`）、语义支持判定（`_check_claim_semantics`）、知识库证据重排（`rerank_evidence`）。它们恰好是**「LLM 只做分类不做生成」**这一论点的三个可检验载体（E30）。

### 2.6 R1 × R4 的联合：模态信息如何改变协同

这是本方向最有研究价值、也最容易被做浅的一处。**不是**"多模态 + 多智能体"的简单叠加，而是问：

> **当证据包里多了一个模态，三类主体之间的冲突结构会不会改变？**

| 可检验的子命题 | 观测指标 |
|---|---|
| 文本模态引入**更多偏好差异**（同向但阈值不同）而非事实冲突 | `ConflictType` 分布：`preference` 占比上升 |
| 文本模态引入**新的事实冲突**（不同角色读到不同的新闻样本） | `fact` 冲突数上升；`duplicate_evidence` 下降（证据去重压力上升） |
| 交叉验证在文本模态下**更难**（数值可重算，文本需判断口径） | `verdict == 'uncertain'` 比例上升；`cross_validation` 阶段 `latencyMs` 上升 |
| 证据链在文本模态下**更关键**（文本更容易幻觉） | `unsupported_claim_rate` 在 `modality.text = true` 时更高（若成立，说明证据链约束有实际价值） |

这四条都**不需要新造数据**，只需要把 `Conflict[]` 与 `VerificationReport` 按模态开关分组统计——而这正是 Agent-Native + 结构化证据链架构的直接副产品。

## 3. 消融设计

### 3.1 消融轴的定义

> **命名约定**：本文用**中文轴名**指代消融维度（角色轴 / 协作轴 / 模态轴 / 增强轴 / 机制轴），用 **`E<编号>`** 指代具体的消融实验条目。两者不是同一套编号，不要混用。

| 轴 | 开关载体（`ExperimentConfig`） | 语义 |
|---|---|---|
| **角色轴** | `agents.roles: List<RoleId>` + `agents.pseudoSpecialize: bool` | 哪些主体参与、以何种专业化程度参与 |
| **协作轴** | `coordination.evidenceShare / crossValidate / coordinate`（对应旧 `ModeFlags`） | 角色之间共享与协调到什么程度 |
| **模态轴** | `modality: {numeric, text, audio, spatial}` | 融合信号包含哪些模态 |

另有两组**扩展轴**（Agent-Native 架构特有或旧项目未系统展开）：

| 轴 | 开关载体 | 语义 | 小节 |
|---|---|---|---|
| **增强轴** | `augment: {rag, tools}` | 工具与知识库是否可用 | §3.5 |
| **机制轴** | `delegation.*` / `crossValidation.maxFindings` / `surfaceStrategy` / `hitl.enabled` / `evidencePacking` | 委派、交叉验证条数、呈现方式、人在环、证据裁剪 | §3.6 |

> **统一要求**：五条轴**必须共用同一条代码路径**（基线 §7.9）。在 Dart 侧，这意味着 `Orchestrator` 的 R0–R5 阶段对所有配置完全相同，只有 `ModeFlags` 与 `ExperimentConfig` 的值不同（见 `docs/03-多智能体架构.md` §2.4）。任何"为了某个消融单独写一条分支"的做法都判定为**实现缺陷**。

### 3.2 角色轴消融

| 编号 | 名称 | 配置 | 检验的假设 |
|---|---|---|---|
| **A0** | 三角色完整 | `roles=[regulator, investor, financing]`, `pseudoSpecialize=false` | 基准 |
| **A1** | 伪分工对照 | `roles=[3]`, `pseudoSpecialize=true`（同 prompt、同工具权限并集） | H1 |
| **A2** | 去监管方 | `roles=[investor, financing]` | 监管视角的系统性判断是否不可替代 |
| **A3** | 去投资方 | `roles=[regulator, financing]` | 组合尾部损失视角是否不可替代 |
| **A4** | 去融资方 | `roles=[regulator, investor]` | 融资成本/再融资视角是否不可替代 |
| **A5** | 单角色单主体 | `roles=[regulator]` | 下界 |
| **A6** | 仅角色不共享证据（协作轴关闭） | `roles=[3]`, `coordination.*=false` | 与 B0 重复，作为交叉校验点 |

**A1 是最重要的一条**：它把"专业化 prompt 的价值"从"多 agent 的价值"里剥离出来。若 A0 ≈ A1，则**多智能体本身没有贡献**，H1 被否证；此时论文的正确结论是"角色化 prompt 有效，但并行多 agent 无增益"，而不是硬说协同有效。

**A2–A4 的解读规则**：去掉某角色后，整体风险等级可能下降（因为该主体的损失权重不再参与合成）——因此**必须同时报告**：
1. 最终等级的变化；
2. `decision_loss` 的变化（合成口径下各主体的期望损失）；
3. 冲突数与核验结论的变化。
只看等级会得出"去掉监管方风险更低 = 更好"的错误结论。

### 3.3 协作轴消融（继承旧 E2–E11）

| 编号 | 名称 | `mode` | `coordination` | 检验 |
|---|---|---|---|---|
| **B0 / E2** | 单智能体（无工具、无知识库） | `single` | 全 false | 基线 |
| **B1 / E3** | 单智能体 + 工具 | `single` | `tools=true` | H3 |
| **B2 / E4** | 单智能体 + 工具 + 知识库 | `single` | `rag=true, tools=true` | H3 |
| **B3 / E5** | 三个独立智能体（无共享、无协调） | `independent` | 全 false | H2 的下界 |
| **B4 / E6** | 协同 - 仅证据共享 | `collaborative` | `share=true, xval=false, resolve=false` | H2 分解 ① |
| **B5 / E7** | 协同 - 证据共享 + 交叉验证 | `collaborative` | `share=true, xval=true, resolve=false` | H2 分解 ② |

> **预算对齐约束** `[已定]`：B0–B8 的**每角色**预算必须一致（`maxToolCallsPerAgent=6`、`maxTokensPerAgent=4000`），一次 run 的总预算 = 参与者数 × 每角色上限。这样 `J = L + μ·C` 的差异**只反映机制本身**，不反映预算宽裕度。协同模式因交叉验证与仲裁消耗执行者预算，实际可用预算更少——这是**真实成本**，应在 `J` 中体现而不是被对齐掩盖。

| 指标 | 定义 | 用途 |
|---|---|---|
| `L`（语言成本） | `tokens/1000 × costPer1kTokens` | 模型开销 |
| `C`（协调成本） | `toolCalls × costPerToolCall + latencyMs × costPerLatencyMs` | 协同税 |
| `μ` | 协调权重（默认 0.1，旧 `app.yaml`） | 量纲换算 |
| `J` | `J = L + μ·C` | **跨模式可比的单一成本指标**（H4） |
| `J_per_decision_loss` | `J / decision_loss` | 性价比 |

### 4.4 质量与安全层（本代新增）

| 指标 | 定义 | 对应基线条目 |
|---|---|---|
| `permission_violations` | 越权工具调用 / 越权信息域引用次数 | §7.5 白名单动作 |
| `leakage_events` | PIT 泄漏次数（`asOf` 或 `releaseTime` 越界） | §7.3 PIT |
| `conflict_escalation_rate` | 冲突升级 HITL 的比例 | §7.8 HITL |
| `hitl_items` / `hitl_approval_rate` | 人工介入项数 / 批准率 | §7.8 |
| `hitl_median_latency_ms` | 人工确认中位耗时（E28） | H5 / E28 |
| `evidence_grade_mix` | 证据等级分布（tool/kb/signal/market 各占比） | 证据链强度 |
| `degraded_role_runs` | 含降级角色的 run 占比 | 可靠性 |

### 4.5 过程指标的采集来源

| 指标 | 来源字段 |
|---|---|
| 协同过程 | `DecisionCard.coordination`（`evidence_shared`/`duplicate_evidence`/`conflicts_*`/`tool_calls`/`tokens`/`latency_ms`/`cost_usd` + 新增 `joint_cost`） |

## 5. 论文级实验协议

### 5.1 数据与窗口

| 项 | 取值 | 来源 |
|---|---|---|
| 样本区间 | `sample_start=2018-01-01`，`sample_end=2025-09-30` | 旧 `p1/p2/p3_*.yaml` |
| 评估起点 | `eval_start=2021-01-01` | 同上 |
| 预热段 | 评估起点之前（滚动窗口需要历史） | 推导 |
| 标签口径 | `label_version=stress_pca_q90`，`high_stress_quantile=0.90` | 旧 `app.yaml` |
| 预测视野 | `horizons=[5, 10, 20]` | 旧 `app.yaml` |
| PIT 快照 | `pit_snapshot=auto`（按 `sources.yaml` 的 `release_lag_days`/`publish_hour`/`tz_offset` 切片） | 基线 §4 |
| 标签热身期 | **评估起点前剔除 ~256 个交易日**（滚动窗口/标签构造需要历史） | 迁移清单 H.56 |
| 样本外判据 | **扩展窗口样本外**：查询时点 `t` 的可用池必须满足 `p + h ≤ t` | 迁移清单 H.52 |

> **口径冻结规则** `[已定·本文]`：一次论文实验批次内，`label_version`、高压力分位、horizons、数据源集合、模态定义**全部冻结**；任一项变更都算**新实验批次**，不得与旧批次结果并列比较。

### 5.2 固定 windows / step

| 项 | 取值 | 理由 |
|---|---|---|
| **windows** | **3** | 基线 §5 R1 明确给出（`windows=3, step=1`） |
| **step** | **1** | 同上；保证每个交易日都是候选起点 |
| **重训周期** | `retrain_every=20`（滚动重训） | 旧 `app.yaml: signal.retrain_every` |
| **滚动窗口长度** | `roll_window=500` | 旧 `app.yaml: signal.roll_window` |

**协议要求**：

1. 三个消融轴的所有配置**共用同一组 (window, step) 网格**，不得为某个配置单独调窗；
2. 网格起点由 `as_of` 与固定 step 决定，**不得**按结果挑选（否则构成 look-ahead）；
3. 滚动重训**只使用窗口内、且 `t+h ≤ R` 截断**的数据（旧语义，见 `CBR-MAW_architecture_v1.md` L2 行）；训练数据与评估数据的边界由 `roll_window` 与 `step` 唯一确定。

### 5.3 样本外（sample-out）

| 层次 | 切分 | 规则 |
|---|---|---|
| **时间维度** | 训练用 ≤ 评估点之前；评估严格在 `eval_start` 之后 | 严禁使用评估点之后的任何数据训练 |
| **标签维度** | 标签 `t+h` 时刻的标签只能用于**评估**，不得进入特征 | 旧 `label_version` 口径 |
| **特征维度** | 融合模型的特征只取 `as_of` 当日可得 | C2（PIT） |
| **LLM 维度** | 角色 prompt 中的证据包全部满足 `asOf` 切片；知识库按 `releaseTime ≤ as_of` 检索 | C2 |
| **扩展窗口维度** | 任何时点 `t` 的可用信息池必须满足 `p + h ≤ t`（`p` 为信息时点，`h` 为视野） | 迁移清单 H.52 |
| **消融维度** | 所有消融配置在**同一评估网格**上评估，样本集合逐日对齐 | 保证配对比较 |

**配对检验的必要性** `[已定·本文]`：由于所有配置共享同一 (window, step) 网格，E0–E30 之间是**逐日配对**的。因此主检验使用**配对自助法（paired bootstrap）**，而不是独立样本检验。旧配置 `eval.bootstrap` 给出试点值（p1=1000，p2/p3=200），本代统一：

| 用途 | bootstrap 次数 | 说明 |
|---|---|---|
| 试点/冒烟 | 200 | 沿用旧 p2/p3 值 |
| **论文正式实验** | **≥ 1000** | 沿用旧 p1 值；报告 95% CI |

### 5.4 统计显著性规则

| # | 规则 | 说明 |
|---|---|---|
| **S1** | 显著性水平 `α = 0.05`（双侧） | |
| **S2** | **必须报告置信区间**，不只报 p 值 | 论文主表同时给 `Δ` 与 95% CI |
| **S3** | **效应量门槛**：只有当 CI **不跨 0** 且 `\|Δ\| ≥ MDE`（最小有意义差）时才宣称"有差异" | `MDE` 需按指标预先设定并写入实验注册表；`[建议·待复核]` 建议：`pr_auc` 的 MDE 取该指标在基线上的一个 bootstrap 标准差的量级 |
| **S4** | **多重比较校正**：同一消融族内的多重检验用 **Holm-Bonferroni**；族定义为「同一假设下的全部对照」（如 H2 族 = {E5, E6, E7, E9, E10, E11}） | 不校正会显著抬高假阳性率 |
| **S5** | **不显著就是结论**：任何未通过 S3 的对照，必须在论文中以"未观察到显著差异"表述，**不得**改写为"略有提升" | 与仓库规约一致（`AGENTS.md` §7） |
| **S6** | **LLM 非确定性**：所有涉及 LLM 的配置，**每个评估网格点至少重复 3 次**（不同随机种子），报告 run 间标准差；主表报**跨 run 平均** | 单次运行的差异不可信 |
| **S7** | **成本比较用配对差**：`ΔJ` 也用配对 bootstrap，并报告 `ΔJ` 与 `Δdecision_loss` 的**比值**及其 CI | H4 的判定依据 |
| **S8** | **不得事后挑选窗口**：若某配置在多个窗口下表现不同，必须**全部报告**并解释，不得只报最好的那个 | |
| **S9** | **失败 run 的处理**：因 LLM 失败导致角色缺席的 run **不得**用规则模板补齐后计入统计（违反 C1）；必须**从主统计中剔除并单独披露失败率** | 失败率本身是结果指标，不是噪声 |
| **S10** | **条件路径类指标**（分位路径、类比条件预测）额外要求 **CRPS + Diebold-Mariano 检验 + PIT 校准率**三者齐备，且 **AW-LP 双口径**（水平 vs 增量锚定）**只有同口径才可比**；并同时报告**反例对照** `p_A`（类比率）/ `p_C`（反例率）/ `p_base`（基础率）/ `lift` | 迁移清单 H.53–H.57 |

### 5.5 预算对齐与公平性

| 规则 | 内容 |
|---|---|
| **F1** | 所有配置**每角色**预算一致：`maxToolCallsPerAgent=6`、`maxTokensPerAgent=4000` |
| **F2** | 一次 run 的总预算 = 参与者数 × 每角色上限；`single` 模式的参与者数按 3 计（它承担三个主体的任务） |
| **F3** | 协同模式下交叉验证与仲裁消耗**执行者**预算，因此可用预算自然少于独立模式——**不额外补偿**（补偿会掩盖真实的协调税） |
| **F4** | `μ`（协调权重）在论文中**必须做敏感性分析**：至少取 μ ∈ {0, 0.1, 0.5} 三档，报告 H4 结论在哪个 μ 区间内成立 | 若结论只在 μ=0 时成立，说明协同的价值仅在于质量而非经济性，必须如实写 |

### 5.6 复现性

| 项 | 要求 |
|---|---|
| **随机性** | 固定并公布：模型 temperature、seed（若模型支持）、数据切分、标签口径 |
| **可复现锚点** | 每个 run 的 `RoleArtifact` 携带 `promptHash` + `modelId` + `toolCalls[].inputsHash`；`DecisionCard.traceRef` 指向 JSONL 审计 |
| **产物落盘** | 每个实验批次产出：配置快照、逐日指标、CI、trace 索引、决策卡样本 |
| **第三方复核** | 因纯客户端单进程（基线 §2），复核者只需一个安装包 + 一个 API 密钥即可重跑；**复核成本本身就是一项可报告的复现性指标** |

### 5.7 硬性声明规范

| # | 声明 | 适用范围 |
|---|---|---|
| **C3.1** | **SYNTHETIC / 仿真数据的结果，只能表述为"在合成数据上的方法学验证"，不得表述为真实市场结论、不得表述为对真实风险的预测能力。** | 所有使用 `data/samples/` 之类合成集的实验 |
| **C3.2** | 每张结果表的表头或脚注**必须**标明数据性质：`真实市场数据（来源台账见 §6.2）` 或 `SYNTHETIC 仿真数据（仅方法学验证）` | 全部表格 |
| **C3.3** | **试点与正式结果分开报告**，表头分别标 `PILOT` 与 `FINAL`；两者不得混列 | 全部表格 |
| **C3.4** | 若某结论只在合成数据上成立，论文中必须写明"该结论未在真实数据上验证" | 全部结论 |
| **C3.5** | 旧项目的 Mock 模式结果（旧架构文档记录的试点数字）**只能作为"方法学可行"的引用**，且必须显式标注为 Mock 语境 | 引用旧结果处 |

> **为什么这条这么严**：跨境金融风险是一个**会被误用的**领域。把仿真结论写成真实市场结论，风险不是学术瑕疵，而是下游误决策。本条因此是**写作规范**而非实验洁癖。

## 6. 威胁与局限（Validity Threats）

### 6.1 内部效度（Internal Validity）

| 威胁 | 缓解措施 |
|---|---|
| **模式混淆**：协同模式同时改变了「是否多 agent」「是否共享证据」「是否协调」 | 用 B4/B5/B6/B7/B8 的**逐项加减**分解，而不是只比 B3 vs B6 |
| **专业化混淆**：「多 agent 的收益」与「角色 prompt 的收益」 | **E8（A1）伪分工对照**是唯一能分离二者的设计，必须在主表 |
| **预算混淆**：协同消耗更多预算 | F1–F3；并用 `ΔJ` 显式报告 |
| **LLM 随机性**：单次运行的差异可能是噪声 | S6（≥3 次重复 + run 间方差） |
| **实现路径差异**：不同配置走了不同代码 | 五条轴必须共用同一条 R0–R5 路径；代码评审时逐轴核对 |
| **呈现层泄漏**：Agent 生成界面可能展示了固定模板没有的信息 | E26 两组必须看到**完全相同的 `DecisionCard`** |

### 6.2 外部效度（External Validity）

| 威胁 | 说明与处理 |
|---|---|
| **单一市场/单一时期** | 数据源集合、时区、交易日历按 `sources.yaml` 声明；跨市场结论需注明覆盖范围 |
| **标签口径依赖** | `stress_pca_q90` 是一种口径；应做**稳健性标签**检验（不同分位/不同标签定义），把标签口径敏感性作为附录表 |
| **角色集合的现实性** | 三类主体是**抽象主体**（监管者 / 组合管理者 / 资金部门），不是具体机构；结论外推到具体机构需谨慎表述 |
| **中文语料偏差** | 媒体基调以中文财经报道为主；外推到英文/其他语种需重新验证 |
| **数据可得性偏差** | 旧项目已记录「北向 2024-08-16 后停披露、CPI 2015–2020 缺失」（`ref/docs/architecture/CBR-MAW_architecture_v1.md`）等口径说明；这些**必须**在论文中显式列出，并作为**来源台账**的一部分（基线 §4 第 3 档：不可达源要显式列原因） |

### 6.3 构念效度（Construct Validity）

| 风险 | 说明 |
|---|---|
| **"协同"的度量** | 用 `decision_loss` 代理"协同价值"是**代理指标**，不是直接测量。需辅以过程指标（冲突率、证据共享率、重复证据率）三角验证 |
| **"决策质量"的代理** | 合成卡上的风险等级 ≠ 真实决策质量。若有专家标注集，可加入"与专家判断的一致率" |
| **"Agent-Native 更好"的构念** | E26 测的是"呈现效率"，不等于"更好的决策支持"。论文表述须限定在可测量的范围内 |
| **偏好差异被误判为冲突** | 冲突分类器（fact/directional/preference）本身是人工设计的规则；需报告其**分类准确性**（可用人工标注样本核） |

### 6.4 结论效度（Conclusion Validity）

| 风险 | 处理 |
|---|---|
| **把不显著写成提升** | S5 |
| **只报有利指标** | 预注册（pre-register）主指标与次指标；主表同时报"变差的指标" |
| **从 pilot 跳到 final** | C3.3 |
| **把方法学验证当市场结论** | C3.1–C3.5 |

## 7. 写作与呈现规范（对论文与对外报告）

### 7.1 结果表的最小元数据

每张结果表必须携带以下元数据（缺一不可）：

```
表 X：<实验编号与名称>
├─ 数据性质：真实市场数据 | SYNTHETIC 仿真数据（仅方法学验证）   ← C3.2
├─ 状态：PILOT | FINAL                                            ← C3.3
├─ 窗口：windows=3, step=1；评估区间 [eval_start, sample_end]
├─ 标签：label_version=..., horizons=[...]
├─ 预算：每角色 maxToolCalls=6 / maxTokens=4000；run 总预算=参与者数×每角色
├─ 重复：n=3（不同种子），run 间标准差=...
├─ 指标与统计量：Δ、95% CI（paired bootstrap, B=1000）、Holm 校正后的 p
└─ 数据缺口说明：<停披露/缺失/授权限制，逐条列出>                ← 基线 §4 第 3 档
```

### 7.2 结论句式规范

| 允许 | 禁止 |
|---|---|
| 「在 X 条件下，A 相对 B 的 `pr_auc` 提升 Δ（95% CI [a, b]），Holm 校正后 p<0.05」 | 「A 显著优于 B」（不报 CI） |
| 「未观察到显著差异（95% CI 跨 0）」 | 「A 略有提升」 |
| 「该结论仅在合成数据上验证，未在真实数据上检验」 | 「实验证明本方法对真实市场有效」（若只有合成数据） |
| 「在 μ∈[0, 0.1] 区间内，协同的决策损失下降幅度超过其 J 增量」 | 「协同是划算的」（不给 μ 区间） |
| 「本次评估中该角色因模型调用超时降级（占 run 的 x%）」 | 隐去降级 |
